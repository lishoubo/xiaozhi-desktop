# 服务端需求：携程价量态定时扫描差异上报（inventoryDiff）

> 面向 rms-server。desktop 侧实现见 `openspec/changes/add-ota-inventory-scan/`。
>
> **服务端工作量预估：新增一个 `AppChangeTranslator` 的 `@Component`，不改任何现有代码。**

## 1. 背景：这条上报解决什么

现有三类上报**都跟在用户操作后面**：

```
price / roomStatus    用户在我们 app 里改了什么      ← 写请求报文
inventoryReadback     用户改完后渠道实际是什么       ← 改完主动读回
```

前提是「变更必然经过我们」。有两类场景不成立，**我们收不到任何信号**：

| # | 场景 | 为什么现有链路抓不到 |
|---|---|---|
| 1 | 用户在**其他浏览器** / 手机 / 渠道 App 上改价 | 请求根本没经过我们 |
| 2 | **无人操作**，渠道自行变更（订满自动关房、活动到期、渠道侧批量调整） | 不存在任何写请求 |

所以 desktop 增加一条**主动对账**链路：定时（默认 5 分钟）取回渠道当前价量态，与本地基线
逐格比对，**只把有差异的格子**报上来。

```
定时器 → 取回渠道当前状态 → 与本地基线比对 → 有差异 → 上报（本需求）
```

## 2. 接入方式

**复用现有端点 `POST /api/v1/app/ota-changes`，报文结构不变。**

新增一个分派键：

| 字段 | 取值 |
|---|---|
| `source` | `ctrip` |
| `changeType` | **`inventoryDiff`** ← 新值 |
| `endpointId` | **`inventoryScan`** ← 新值，**服务端按它分派 Translator** |

⚠️ **`changeType` 是新值，DTO 的枚举校验若是白名单，需要加上 `inventoryDiff`**，
否则整条上报会在入口被拒。

⚠️ 服务端按 `(source, endpointId)` 分派，`changeType` 只进日志、不参与分流 —— 所以
**必须为 `(ctrip, inventoryScan)` 写一个 Translator**。不写的话 desktop 照常发送、
服务端回 `PARSE_FAILED` 或 `SKIPPED`（那是 `code=0` 的**正常响应**，上报是单向通知），
**desktop 这侧看不出任何异常**，会一直白发。

## 3. 报文

```json
{
  "operationId": "3f2a…",
  "source": "ctrip",
  "changeType": "inventoryDiff",
  "endpointId": "inventoryScan",
  "endpointUrl": "https://ebooking.ctrip.com/ebkovsroom/api/inventory/getRoomInventoryInfo",
  "otaHotelId": "122244992",
  "channelAccountId": "12779987",
  "channelAccountName": "运营商赵经理",
  "submitAt": "2026-09-20T10:00:03.000Z",
  "changeRaw": {
    "probedAt": "2026-09-20T10:00:03.000Z",
    "cells": [ … ]   // 每格带 itemType，见 §4.2
  }
}
```

`changeRaw` **只有两个字段**：

| 字段 | 含义 |
|---|---|
| `probedAt` | 本轮扫描取回数据的时刻 |
| `cells` | **只含有差异的格子**，渠道原始行 |

⚠️ 刻意**没有** `trigger` 和 `truncated`（回读上报里有）：扫描由定时器触发，没有对应的
用户操作可指；扫描窗口由配置决定且完全可知，不存在「数据可能不完整」的情况。

## 4. ⚠️ `cells` 的结构 —— 本文档最关键的一节

### 4.1 房态房量是**一条**，价格是**另一条**

同一个房型、同一天，**可能出现两条 cell**：

```json
// 第一条：房态 + 房量
{
  "itemType": "roomStatus",
  "hotelID": 122247738,
  "roomTypeID": 1569052074,
  "effectDate": "2026-10-20",
  "payType": "PP",
  "roomStatus": "G",
  "limitSale": "T",
  "freeSale": "F",
  "totalQuantity": 7,
  "canUsedQuantity": 7,
  "hasInventory": true
}

// 第二条：价格
{
  "itemType": "price",
  "roomTypeID": 1569052074,
  "effectDate": "2026-10-20",
  "payType": "PP",
  "price": 434,
  "cost": 229.5,
  "commissionRate": 0.15,
  "currency": "RMB",
  "originalPrice": 434
}
```

**为什么分两条**：携程的读接口本来就分两个数组返回 ——
`data.roomStatusResult[]`（房态房量，一行含两者）与
`data.roomPriceResult.roomPriceInfo[]`（价格）。desktop **原样透传，不做重组**。

⚠️ **不可假设两者成对出现**：携程的价格路径**可能不覆盖全部格子**（关房的日期没有价格行）。
真机实测某门店：房态 437 行、价格 346 行，**91 格有房态无价格**。
**「有房态没价格」是正常的，不是数据缺失。**

### 4.2 靠什么区分两类 cell

**每个 cell 自带 `itemType` 字段：**

| `itemType` | 类型 | 房型标识 |
|---|---|---|
| `roomStatus` | 房态房量 | `roomTypeID` |
| `price` | 价格 | `roomTypeID` |

> 📌 **2026-09-21 变更**：原先这里写的是「desktop 不会加类型标记字段，看字段特征判断
> （有 `roomStatus` 就是房态、有 `price` 就是价格）」。**已改为显式带 `itemType`**。
>
> 起因是美团接入：**美团两类 cell 的房型 ID 空间不同**（房态房量挂 `roomId` 物理房型、
> 价格挂 `goodsId` 售卖商品），猜错会拿 `goodsId` 去查物理房型 —— 查不到，或更糟：
> 查到一个同号的别的房型。
>
> 而基线库里本就有这一维（`item_type` 列），只发渠道原始行等于把它丢掉。
> 两个渠道一并加上，Translator 结构保持一致。
>
> 携程这边字段特征判断本来也够用（两类共用同一个 `roomTypeID`），但**建议改用
> `itemType`** —— 它是权威的，字段特征是推断的。

### 4.3 一条上报里可能同时有价、量、态

`changeType` 叫 `inventoryDiff` 而不是 `inventoryPrice`/`inventoryStatus`，正是因为
一轮扫描发现的差异是**混合的**：可能这个房型价格变了、那个房型关房了、另一个房量少了，
全部放在同一条上报的 `cells` 里。

**服务端必须遍历 `cells` 逐格判断类型，不能按 `changeType` 假设全是某一类。**

### 4.4 字段语义

与 `inventoryReadback` 的 cells **完全相同**（同一个接口的同一批字段），逐字段含义见
`add-ctrip-inventory-readback/服务端需求.md`，此处不重复。三条要点摘录：

- ⚠️ **`limitSale: "F"` 时房量 0 不代表没房**。判读顺序：先看 `freeSale === "T"`（不限量），
  否则看 `limitSale`，为 `"T"` 才读房量数字
- ⚠️ **`cells[].hotelID` 不可用于匹配门店** —— 它是「门店 × 售卖模式」层的标识（同店预付
  与现付各一个）。匹配门店请用**顶层 `otaHotelId`**（已用凭证归一过）
- **枚举原样透传**：`roomStatus` 是 `"G"`(开) / `"N"`(系统关) / `"Y"`(手动关)；
  `limitSale`/`freeSale` 是 `"T"`/`"F"` 字符串，不是布尔

## 5. ⚠️ 与回读上报的三条差异（影响怎么解读）

### 5.1 `cells` 只含**有差异的**格子，不是完整快照

回读的 `cells` 是「本次改动涉及的房型 × 日期」的**全量**读回结果；本上报的 `cells` 是
「与本地基线比对后**变了的**」那些格子。

### 5.2 ⚠️ **「没报」不等于「没变」**

desktop 的本地基线是**逐步积累**的（用户浏览页面时旁听、改动后回读）。扫描时若某格
**从未见过**，它会被写入基线但**不上报** —— 因为「没有基线」不等于「渠道新增了」，
多半只是我们从没读到过那一格。

不这么做的后果：首次扫描会把整个窗口（15 天 × 全部房型）当成变更灌给服务端。

**所以「某格没出现在 cells 里」有两种可能**：确实没变，或那一格是第一次见。
**本上报区分不了这两者，服务端也不应据此推断。**

### 5.3 与用户操作无关

`inventoryReadback` 总是跟在一次用户改动后面；`inventoryDiff` **与用户操作无关**。
`loginUserId` 对这条上报没有业务含义（服务端以 JWT 为准，desktop 本就不发这个字段）。

## 6. 其他须知

- **扫描窗口**：默认从今天起 **15 天**（与携程页面一次返回的范围对齐），可配置
- **频率**：默认每轮结束后歇 5 分钟 + 0~1 分钟随机抖动。⚠️ 是 **fixed-delay**
  不是固定频率，实际间隔 = 本轮耗时 + 5~6 分钟
- **幂等**：`operationId` 每次上报独立生成。同一格连续两轮都变会产生两条上报，
  **不可互相去重** —— 它们是两次不同的观测
- **偶发漏报是已知取舍**：扫描失败不重试、不补扫，下一轮自然覆盖
- **只有携程**：美团/抖音本期不接入。美团的价格挂售卖房型（`goodsId`）而房量挂物理房型
  （`roomId`），ID 空间不同 —— ✅ **已接入**，cells 结构的处理见
  `add-meituan-inventory-scan/服务端需求.md`（靠 `itemType` 分派，本文档 4.2 那条变更
  正是为它而加）
