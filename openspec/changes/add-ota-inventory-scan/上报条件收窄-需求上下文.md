## 当时的阻塞项与最终答案

本文当时写着「必须先真机对照才能定字段口径，不要跳过第 1 步直接写判据」。
实际做法是**从本地快照库挖真机数据**（携程 755 行 / 美团 201 行，2026-09-22），
不必手工造样本。结论：

| 概念 | 携程 | 美团 |
|---|---|---|
| 总房量 | `totalQuantity`（限量时才读） | `limitRemain + usedCount` |
| 可售为 0 | `hasInventory === false`（限量时才读） | `limitType === 1 && limitRemain === 0` |

判据：房态与价格维持「有改变就报」；房量仅在**总房量变化**或**可售从非 0 变为 0**
（只报跃迁）时上报。

## ⚠️ 本文当时写错的三处

保留这一节是因为这些说法来自当时的代码注释与旧文档，**在别处可能还有残留**。

### 1. 「`remainCount` 剩余可卖」「`remainCount + usedCount` 还原出总量」

**都错。** `remainCount` 是**预留房量**，与 `limitRemain` / `usedCount`
**没有算术关系**（实测多为 0、偶尔 1，而同格 `limitRemain` 可达 39）。

「`remainCount + usedCount` = 物理房量」的说法也不成立 —— 云舒双床房照此算出 2，
而该房型配额有 40。**判据完全不用这个字段。**

### 2. 「`limitRemain` 与 `remainCount` 语义上像是同一个东西，没有踩点数据能区分」

有数据能区分，而且区别很大：201 行里 `remainCount ≤ limitRemain` 恒成立
（199 行严格小于），两者从来不是一回事。

### 3. 「`hasInventory` 是携程自己的有房标记」→ 因此可以直接采信

**证伪。** `canUsedQuantity = 0` 且 `freeSale = "T"` 的 68 行（文档明写**有房**），
`hasInventory` **全部为 false** —— 不限量的房型在这个字段上与真售罄长得一模一样。
必须**先判不限量、再读数字**，裸用会把这 68 行全判成售罄。
