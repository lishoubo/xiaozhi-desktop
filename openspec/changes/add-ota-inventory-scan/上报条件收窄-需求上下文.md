# 房量上报条件收窄 —— 上报逻辑

> 实现见 `openspec/changes/narrow-inventory-report-criteria/`
> （`design.md` = 怎么做，`服务端需求.md` = 给服务端的口径说明）。

## 背景

旧判据是「`contentHash` 里任一字段变了就报」。酒店**有订单时房量本来就会变**
（卖出一间 → 已售 +1、剩余 −1），这类正常销售被当成渠道变更报上去，导致房量上报过于频繁。

## 上报判据

```
一格发生变化
   │
   ├─ 价格 ─────────────────────────────→ 上报（维持原样）
   │
   └─ 房态房量
         ├─ ① 房态变了 ─────────────────→ 上报
         ├─ ② 限量 ⇄ 不限量 切换 ───────→ 上报
         ├─ ③ 限量下，可售「非 0 → 0」──→ 上报（只报跃迁那一轮）
         ├─ ④ 限量下，总房量变了 ───────→ 上报
         └─ 其余（纯卖房）──────────────→ 不报
```

**首次见到的格子只写基线、不上报**（基线天然稀疏，把「没读过」当成「渠道新增了」
会在首轮把整个窗口灌给服务端）——这条是既有行为，本次未改。

## 字段口径

### 判「限量还是不限量」

| 渠道 | 判据 |
|---|---|
| 携程 | 先看 `freeSale === "T"` → 不限量；否则看 `limitSale`，**只有 `"T"` 才是限量** |
| 美团 | `limitType === 1` 是限量，`2` 是不限量 |

⚠️ **顺序不可颠倒**。不限量时两个渠道的房量数字都**没有意义**：

- 携程不限量时 `totalQuantity` / `canUsedQuantity` 本来就是 0，但**实际有房**

  ⚠️ **同一个 0 在两种模式下含义相反**（实测 755 行）：

  | 模式 | `totalQuantity` | `canUsedQuantity` | 含义 |
  |---|---|---|---|
  | 不限量 | 0 | 0 | **有房**，数字无意义 |
  | 限量 | **从不为 0**（实测最小 2） | > 0 | 有房 |
  | 限量 | **从不为 0** | **0** | **真售罄** ← 判据要捕获的 |

  所以「可售为 0」必须**先判模式再读数字** —— 不限量那 68 行若按数字判会全成售罄。
- 美团不限量时 `limitRemain` 是哨兵值（实测见过 998 / 999 / 1002，**不是固定几个数**）

所以不限量的格子**不参与 ③ ④ 两条房量判据**，只有 ① ② 还管它。

### 限量时读哪个字段

| 概念 | 携程 | 美团 |
|---|---|---|
| 总房量 | `totalQuantity` | `limitRemain + usedCount` |
| 可售房量 | `canUsedQuantity` | `limitRemain` |

**美团的总房量是算出来的**：`limitRemain` 是「配额 − 已售」，加回 `usedCount` 才是
用户设的配额。实测云憩大床房 15 个日期上该和恒为 20（其间 `usedCount` 从 0 变到 5）——
**卖出一间时 `limitRemain` −1、`usedCount` +1，和不变**，这正是「有订单不误报」
所依赖的不变量。

⛔ **美团 `remainCount` 是预留房量**，不是「剩余可卖」，与 `limitRemain` / `usedCount`
无算术关系，判据完全不用它。

⛔ **携程 `hasInventory` 不能用来判售罄**：限量的 291 行里它**恒为 `true`**，
拿它判等于写一条永不触发的死代码。（它为 `false` 的 203 行全部落在不限量，
而那些行按上面的顺序已经被滤掉了。）

## 三个未文档化的取值（实测）

| 字段 | 取值 | 场景 |
|---|---|---|
| 美团 `limitRemain` | `1002` | `limitType=2`，哨兵值家族不止 998/999 |
| 美团 `roomStatus` | `100` | 真卖光时，`fullRoomDesc`:「请补充房型库存」 |
| 美团 `fullRoomCode` | `4` | 同上（既有样本只见过 `3`） |

⚠️ `roomStatus = 100` 是 `0`/`1` 之外的**第三态**。desktop 不解读取值（房态判据是
「有改变就报」），但服务端若按 `0/1` 二值分派会漏掉它。

## ⭐ 上报的**内容**没变，只是**时机**变了

这是本次变更对服务端唯一需要交代的事：

| | 变更前 | 变更后 |
|---|---|---|
| **什么时候报**（触发条件） | 任一 hash 字段变了就报 | **收窄成上面四条** |
| **报什么**（报文） | — | **完全不变** |

### 报文结构（未变，照抄现状）

```json
{
  "operationId": "3f2a…",
  "source": "ctrip",              // 或 meituan
  "changeType": "inventoryDiff",
  "endpointId": "inventoryScan",
  "otaHotelId": "122244992",
  "changeRaw": {
    "probedAt": "2026-09-20T10:00:03.000Z",
    "cells": [
      { "itemType": "roomStatus", "roomTypeID": 1569052074, "effectDate": "2026-10-20",
        "roomStatus": "G", "limitSale": "T", "totalQuantity": 7, "canUsedQuantity": 7 },
      { "itemType": "price", "roomTypeID": 1569052074, "effectDate": "2026-10-20",
        "price": 434, "currency": "RMB" }
    ]
  }
}
```

**逐项确认没变**：

| 项 | 状态 |
|---|---|
| `source` / `changeType` / `endpointId` | 不变（分派键没动，Translator 不用改） |
| `changeRaw.probedAt` / `changeRaw.cells` | 不变 |
| 每个 cell 的字段 | 不变 —— 仍是**渠道原始行整行透传** + 我们加的 `itemType` |
| 枚举取值 | 不变（`"G"`/`"N"`/`"Y"` 不转开关，`"T"`/`"F"` 不转布尔） |
| 金额单位 | 不变（美团仍是「分」的字符串） |

⛔ **判据算出来的数字不进报文**。desktop 为了决定「发不发」会算
`limitRemain + usedCount`，但这个结果**不写进 cell** —— 报文里依旧只有渠道原字段。
服务端若需要「用户设了多少房」，仍按上面「字段口径」一节自行计算。

### 对服务端代码的影响

**零改动。** 不用改 DTO、不用改 Translator、不用加枚举值。

### 但有两件事服务端要知道

**1. 上报量会明显下降**，若有基于旧频率的告警阈值或容量假设，需要下调。

**2. ⚠️「不再收到某格的上报」是预期行为，不是 desktop 故障。**
有订单的房型每轮房量都在变，但只要配额没变、也没售罄跃迁，就不会再报。

⚠️ 这一条和既有的「首次见到不上报」叠加后，**「没收到」有三种可能**：

```
① 渠道确实没变
② 那一格是第一次见（只建基线、不上报）  ← 既有行为
③ 变了，但判据认为不值得报（纯卖房）    ← 本次新增
④ 本轮基线太旧，整批跳过比对            ← 本次新增，见下
```

报文本身区分不了这三种。desktop 侧日志能区分（`changed` 与 `reported` 两个计数，
差额即被滤掉的销售噪音），但那是本地日志，服务端看不到。

## 不在本次范围

- **不改上报体**：报文结构、字段、`changeType` / `endpointId` 全部不变，只是发得少了。
  判据算出的总房量**不写进报文**，语义解读仍是服务端的事。
- **不改 `contentHash`**：`HASH_FIELDS` 与其顺序一动，既有基线全失效，
  下一轮扫描会把整个窗口判成变更。
- **不做 `changedFields`**（报「变了什么」而非「现在是什么」）：仍是独立待办。
- **不区分「关房」与「售罄」**：依赖未踩实的 `invSwitch` 语义，房态判据维持现状故不需要。
