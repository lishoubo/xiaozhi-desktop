# 房量上报条件收窄 —— 上报逻辑

> 实现见 `openspec/changes/narrow-inventory-report-criteria/`
> （`design.md` = 怎么做，`服务端需求.md` = 给服务端的口径说明）。

## 背景

旧判据是「`contentHash` 里任一字段变了就报」。酒店**有订单时房量本来就会变**
（卖出一间 → 已售 +1、剩余 −1），这类正常销售被当成渠道变更报上去，导致房量上报过于频繁。

## 上报判据

```
一格发生变化
   │
   ├─ 价格 ─────────────────────────────→ 上报（维持原样）
   │
   └─ 房态房量
         ├─ ① 房态变了 ─────────────────→ 上报
         ├─ ② 限量 ⇄ 不限量 切换 ───────→ 上报
         ├─ ③ 限量下，可售「非 0 → 0」──→ 上报（只报跃迁那一轮）
         ├─ ④ 限量下，总房量变了 ───────→ 上报
         └─ 其余（纯卖房）──────────────→ 不报
```

**首次见到的格子只写基线、不上报**（基线天然稀疏，把「没读过」当成「渠道新增了」
会在首轮把整个窗口灌给服务端）——这条是既有行为，本次未改。

## 字段口径

### 判「限量还是不限量」

| 渠道 | 判据 |
|---|---|
| 携程 | 先看 `freeSale === "T"` → 不限量；否则看 `limitSale`，**只有 `"T"` 才是限量** |
| 美团 | `limitType === 1` 是限量，`2` 是不限量 |

⚠️ **顺序不可颠倒**。不限量时两个渠道的房量数字都**没有意义**：

- 携程不限量时 `totalQuantity` / `canUsedQuantity` 本来就是 0，但**实际有房**
- 美团不限量时 `limitRemain` 是哨兵值（实测见过 998 / 999 / 1002，**不是固定几个数**）

所以不限量的格子**不参与 ③ ④ 两条房量判据**，只有 ① ② 还管它。

### 限量时读哪个字段

| 概念 | 携程 | 美团 |
|---|---|---|
| 总房量 | `totalQuantity` | `limitRemain + usedCount` |
| 可售房量 | `canUsedQuantity` | `limitRemain` |

**美团的总房量是算出来的**：`limitRemain` 是「配额 − 已售」，加回 `usedCount` 才是
用户设的配额。实测云憩大床房 15 个日期上该和恒为 20（其间 `usedCount` 从 0 变到 5）——
**卖出一间时 `limitRemain` −1、`usedCount` +1，和不变**，这正是「有订单不误报」
所依赖的不变量。

⛔ **美团 `remainCount` 是预留房量**，不是「剩余可卖」，与 `limitRemain` / `usedCount`
无算术关系，判据完全不用它。

⛔ **携程 `hasInventory` 不能用来判售罄**：限量的 291 行里它**恒为 `true`**，
拿它判等于写一条永不触发的死代码。（它为 `false` 的 203 行全部落在不限量，
而那些行按上面的顺序已经被滤掉了。）

## 三个未文档化的取值（实测）

| 字段 | 取值 | 场景 |
|---|---|---|
| 美团 `limitRemain` | `1002` | `limitType=2`，哨兵值家族不止 998/999 |
| 美团 `roomStatus` | `100` | 真卖光时，`fullRoomDesc`:「请补充房型库存」 |
| 美团 `fullRoomCode` | `4` | 同上（既有样本只见过 `3`） |

⚠️ `roomStatus = 100` 是 `0`/`1` 之外的**第三态**。desktop 不解读取值（房态判据是
「有改变就报」），但服务端若按 `0/1` 二值分派会漏掉它。

## 不在本次范围

- **不改上报体**：报文结构、字段、`changeType` / `endpointId` 全部不变，只是发得少了。
  判据算出的总房量**不写进报文**，语义解读仍是服务端的事。
- **不改 `contentHash`**：`HASH_FIELDS` 与其顺序一动，既有基线全失效，
  下一轮扫描会把整个窗口判成变更。
- **不做 `changedFields`**（报「变了什么」而非「现在是什么」）：仍是独立待办。
- **不区分「关房」与「售罄」**：依赖未踩实的 `invSwitch` 语义，房态判据维持现状故不需要。
