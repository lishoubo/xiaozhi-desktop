## 需求

现状：`contentHash` 里任一字段变了就上报。真机观察到**房量上报过于频繁** ——
根因是酒店有订单时房量本来就会变（这一点此前评审时提醒过，现在被真机证实）。

用户要求把房态与房量**分成两条判据**：

| 类别 | 上报条件 |
|---|---|
| **房态** | 有改变就报（**与现状一致，不动**） |
| **房量** | ① 总房量变化；或 ② 可售房量为 0 |

> 用户原话：「房量这个需要看看」—— 即房量这条判据的字段口径需要先确认，
> 不是直接照上面两句写代码。

---

## ⚠️ 为什么不能直接写：两个渠道的字段名与语义都不同

`contentHash` 目前是**一个 hash 覆盖房态 + 房量所有字段**，两者混在一起，
没有「哪个字段变了」的粒度。要分开判据，必须先确定每个渠道的「总房量」
和「可售房量」分别是哪个字段。

### 携程（`inventory-snapshot/ctrip-cells.ts` 的 `HASH_FIELDS`）

```
roomStatus        房态本身（"G" 开 / "N" 系统关 / "Y" 手动关）
limitSale         是否限量。⚠️ "F" 时房量 0 **不代表没房**
freeSale          FreeSale 标记。判读顺序：先看它，再看 limitSale
totalQuantity     ← 疑似「总房量」
canUsedQuantity   ← 疑似「可售房量」
hasInventory      携程自己的有房标记
```

⚠️ **`limitSale` / `freeSale` 是坑**：注释明写「`limitSale` 为 `"F"` 时房量 0
**不代表没房**」。所以「可售房量为 0 就报」这条判据**不能只看
`canUsedQuantity === 0`**，要先过 `freeSale` / `limitSale` 的判读顺序。
详见 `channels/ctrip/inventory-readback-payload.ts` 的「四条反直觉约定」。

### 美团（`inventory-snapshot/meituan-cells.ts` 的 `ROOM_STATUS_HASH_FIELDS`）

```
roomStatus     房态本身
limitType      是否限量 —— 它变了，limitRemain 的含义就变了
limitRemain    ⚠️ 是「配额 − 已售」，**不是**用户设的配额本身
remainCount    剩余可卖
usedCount      已售。与 remainCount 一起才能还原出总量
invSwitch      房态开关
```

⚠️ **美团没有直接的「总房量」字段**。注释说 `remainCount` + `usedCount`
「一起才能还原出总量」—— 也就是总量是**算出来的**，不是读出来的。
而 `limitRemain` 是「配额 − 已售」，它变化既可能是配额变了、也可能是卖了一间。

⚠️ 真机实测过的一条：用户在 web 把云享三人间房量设成 7，`limitRemain` 从 5→7
（见 `STATUS.md` 的 9.3 验证）。**说明用户改配额确实会反映在 `limitRemain` 上**，
但卖出一间也会让它 −1 —— 这正是当前误报的来源。

### 字段对应关系（**待确认，不要当结论用**）

| 概念 | 携程 | 美团 |
|---|---|---|
| 总房量 | `totalQuantity`？ | `remainCount + usedCount`？还是配额？ |
| 可售房量 | `canUsedQuantity`？ | `remainCount`？还是 `limitRemain`？ |

⚠️ 美团那两个问号是真问号：`limitRemain`（配额−已售）与 `remainCount`（剩余可卖）
**语义上像是同一个东西**，但字段集里两个都在、且注释分别写了不同说明。
**没有踩点数据能区分它们**，必须真机对照（改配额 / 卖一间，看两个字段各自怎么动）。

## 已知的相关约束

### 1. `contentHash` 字段顺序不可改

两处注释都写了：**顺序即 hash 拼接顺序，改了会让全部既有基线的 hash 失效，
下一轮扫描把整个窗口判成变更**。加字段只能追加到末尾。

⚠️ 所以实现方式大概率**不是**改 `HASH_FIELDS`，而是在 `snapshot-diff` /
`scan-to-report` 那层加一道「变化是否值得上报」的判断。具体分层待设计。

### 2. 已有一个相关的待办（用户此前决定先不做）

`add-meituan-inventory-scan/STATUS.md` 的
「📌 用户提出但暂不做：上报「变了什么」而非「现在是什么」」：

> 现状是**报整行**，服务端看不出哪个字段变了。desktop 这边其实知道
> （`snapshot-diff` 手里有新旧两个 hash）。若要做，可在 cell 里带
> `changedFields: { limitRemain: {from,to} }`。

⚠️ **本需求可能让这条从「暂不做」变成「顺带就做了」** —— 要判断「总房量变了没」
就必须比对具体字段，而不是只比 hash。两件事在同一层。

### 3. `roomStatus` 与 `invSwitch` 的语义未踩实（美团）

同一份 STATUS 记着：读响应侧这两个字段**我们没有自己踩点**，RPA 文档也明说
`invSwitch`「本期不读」。推论是「两者组合才能区分关房与售罄」，但没验过。

⚠️ 房态那条判据「有改变就报」维持现状，所以本需求**不依赖**解决这个。
但如果后面要区分「关房」和「售罄」，会撞到它。

## 下一步（建议顺序）

1. **先真机确认字段语义**，这是唯一的阻塞项：
   - 携程：改总房量 → 看 `totalQuantity` / `canUsedQuantity` 各自怎么动；
     制造一个「`limitSale='F'` 且房量 0」的格子，确认它不该被判成「可售为 0」
   - 美团：分别做「改配额」和「卖出一间（或模拟 `usedCount` 变化）」，
     看 `limitRemain` / `remainCount` / `usedCount` 三者各自怎么动
2. 定字段对应关系表，填掉上面那张表的问号
3. 再设计判据落在哪一层（`snapshot-diff` 还是 `scan-to-report`），
   以及是否顺带做 `changedFields`
4. 按任务分级：这是**中任务**（多文件、跨两个渠道的映射 + 比对层），
   按 CLAUDE.md 应先 `/opsx:propose` 产出 design.md + tasks.md

⚠️ **不要跳过第 1 步直接写判据** —— 上面那张表里的字段对应关系全是从注释推的，
一个都没有真机对照过。猜错的后果是「该报的不报」，而这种失效在日志上看不出来。
