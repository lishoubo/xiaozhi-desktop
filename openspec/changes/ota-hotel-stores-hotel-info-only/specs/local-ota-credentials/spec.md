## ADDED Requirements

### Requirement: 酒店探测只产出候选，不写入本地记录

系统 MUST 将酒店探测视为**无副作用的查询**：探测结果 MUST NOT 直接写入本地酒店记录。
本地酒店记录 MUST 仅在用户从候选中选定后写入。探测过程 MUST NOT 因该凭证已存在酒店
记录而跳过——用户否决候选后，同一凭证 MUST 能再次探测。

#### Scenario: 探测成功但用户尚未确认

- **WHEN** 某凭证的酒店探测返回一个或多个候选酒店
- **THEN** 系统不创建也不更新任何本地酒店记录
- **AND** 候选结果仅作为本次待确认数据向上传递

#### Scenario: 用户否决后再次探测同一凭证

- **WHEN** 用户对某凭证的候选酒店未作确认（或明确否决）
- **AND** 该凭证再次触发酒店探测
- **THEN** 系统重新执行探测并再次产出候选
- **AND** 系统不因任何既有记录而跳过本次探测

#### Scenario: 探测目标标签页已关闭

- **WHEN** 酒店探测完成时其来源标签页已被关闭
- **THEN** 系统丢弃本次候选结果
- **AND** 系统不写入任何本地酒店记录

### Requirement: 本地只保存酒店信息，不表达绑定关系

本地酒店记录 MUST 只保存渠道酒店自身的信息：所属凭证、渠道、OTA 酒店 ID、酒店名称和
渠道原始上下文。OTA 酒店与 RMS 酒店之间的绑定关系 MUST NOT 保存在本地，该关系由远端
持有。本地记录 MUST NOT 引入表达绑定动作的字段（如绑定时刻、RMS 酒店标识）。

#### Scenario: 用户确认候选酒店

- **WHEN** 用户从候选列表中选定一家酒店并确认
- **THEN** 系统保存该酒店的凭证标识、渠道、OTA 酒店 ID、酒店名称和渠道原始上下文
- **AND** 系统不在本地保存该酒店与任何 RMS 酒店的对应关系

#### Scenario: 查询本地酒店信息

- **WHEN** 系统按渠道与 OTA 酒店 ID 查询本地酒店记录
- **THEN** 返回结果只包含酒店自身信息与所属凭证标识
- **AND** 返回结果不包含绑定关系字段

### Requirement: 同一渠道酒店在本地唯一并跟随最新凭证

同一渠道下的同一 OTA 酒店在本地 MUST 只存在一条记录。保存时若该渠道酒店已存在，系统
MUST 更新既有记录：改为指向本次凭证，并刷新酒店名称与渠道原始上下文；MUST NOT 因重复
而报错，也 MUST NOT 产生第二条记录。

#### Scenario: 首次保存某渠道酒店

- **WHEN** 用户确认的渠道与 OTA 酒店 ID 在本地尚无记录
- **THEN** 系统新建一条酒店记录

#### Scenario: 同一酒店由新凭证再次保存

- **WHEN** 用户确认的渠道与 OTA 酒店 ID 在本地已有记录
- **AND** 本次凭证与既有记录所指凭证不同
- **THEN** 系统将该记录改为指向本次凭证
- **AND** 系统刷新该记录的酒店名称与渠道原始上下文
- **AND** 系统不新增记录、不删除原凭证

#### Scenario: 同一凭证保存多家酒店

- **WHEN** 用户使用同一凭证先后确认两家不同的 OTA 酒店
- **THEN** 系统保留两条分别指向该凭证的酒店记录

## MODIFIED Requirements

### Requirement: 携程从当前登录页面发现酒店

系统 MUST 在触发登录成功的当前携程页面中读取酒店信息，不得为了携程酒店发现创建隐藏
浏览器 View 或重新加载固定管理页。系统 MUST 在读取页面前校验当前页面属于受信任的携程
商家后台 HTTPS 域名。读取所得酒店 MUST 作为候选返回，不得直接写入本地酒店记录。

#### Scenario: 当前页面发现一家酒店

- **WHEN** 当前受信任携程页面包含一家有效酒店的标题链接
- **THEN** 系统从当前页面读取酒店 ID 和名称
- **AND** 系统将该酒店作为候选返回，不写入本地酒店记录

#### Scenario: 当前页面不受信任

- **WHEN** 当前页面不是受信任的携程商家后台 HTTPS 页面
- **THEN** 系统拒绝执行酒店发现脚本
- **AND** 系统不创建或更新 credential 与本地酒店记录

#### Scenario: 当前页面发现多家酒店

- **WHEN** 当前受信任携程页面包含多家有效酒店
- **THEN** 系统返回多酒店候选结果
- **AND** 系统不保存 credential 或本地酒店记录

### Requirement: 美团账号身份与酒店事实分别持久化

系统 MUST 从美团账号详情读取登录账号身份，并从美团酒店列表读取可操作酒店；账号身份
MUST 保存到 `OtaCredential`。酒店 ID、名称和合作方上下文 MUST 作为候选返回，仅在用户
确认后保存为本地酒店记录。系统不得使用酒店 ID 代替美团登录账号 ID。

#### Scenario: 美团账号与单酒店发现成功

- **WHEN** 美团账号详情和酒店列表均返回有效结果
- **THEN** 系统保存或刷新 credential 的渠道账号 ID、附加账号资料和刷新时间
- **AND** 系统将该酒店作为候选返回，不写入本地酒店记录
- **AND** 候选携带美团酒店 ID、名称和合作方上下文

#### Scenario: 美团账号可访问多个酒店

- **WHEN** 美团酒店列表返回多个有效酒店
- **THEN** 系统将全部酒店作为候选返回
- **AND** 所有候选引用本次识别出的同一 credential

#### Scenario: 美团身份读取失败

- **WHEN** 无法取得或校验美团渠道账号 ID
- **THEN** 本次发现明确失败
- **AND** 系统不使用酒店 ID 猜测账号身份
- **AND** 系统保留已有 credential 和本地酒店记录

### Requirement: 抖音账号身份与酒店事实分别持久化

系统 MUST 从当前抖音登录页面同源接口读取登录用户身份，并继续从抖音门店页面响应读取可操作酒店。
登录用户 ID 和白名单资料 MUST 保存到 `OtaCredential`；酒店 ID、名称和商户组上下文 MUST
作为候选返回，仅在用户确认后保存为本地酒店记录。系统不得使用商户组 ID 或酒店 ID 代替
抖音登录用户 ID。

#### Scenario: 抖音账号与酒店发现成功

- **WHEN** 当前页面同源接口返回有效 `user_id` 且酒店发现返回有效酒店
- **THEN** 系统保存或刷新 credential 的渠道账号 ID、附加账号资料和刷新时间
- **AND** 系统将该酒店作为候选返回，不写入本地酒店记录
- **AND** 候选携带抖音酒店 ID、名称和商户组上下文

#### Scenario: 抖音账号身份缺失

- **WHEN** 当前页面同源接口失败、格式无效或没有完整身份字段
- **THEN** 本次发现明确失败
- **AND** 系统不创建或更新 credential 与本地酒店记录

#### Scenario: 抖音账号数据白名单

- **WHEN** 系统处理抖音登录信息接口中的账号资料
- **THEN** 系统只保存用户 ID、登录 ID、名称、角色名称和角色类型
- **AND** 系统不保存原始缓存、cookie、token 或其他未选定字段

### Requirement: 本地酒店保存渠道化原始上下文

系统 MUST 在本地酒店记录的 `bindExtra` 中保存酒店探测阶段获得的渠道原始上下文。该字段名
与服务端保持一致。`bindExtra` MUST 是可空 JSON，并在读写时按渠道校验；系统不得为当前
未确认的字段制造占位值。候选阶段 MUST 携带该上下文，用户确认时原样保存。

#### Scenario: 抖音酒店保存商户组

- **WHEN** 抖音候选结果包含 `groupId`
- **AND** 用户确认该酒店
- **THEN** 系统将其保存为 `bindExtra.merchantGroupId`

#### Scenario: 美团酒店保存合作方信息

- **WHEN** 美团候选结果包含合作方 ID 与名称
- **AND** 用户确认该酒店
- **THEN** 系统将其保存为 `bindExtra.otaPartnerId` 与 `bindExtra.otaPartnerName`

#### Scenario: 携程当前没有额外上下文

- **WHEN** 携程候选结果没有已确认的渠道原始字段
- **THEN** 系统将 `bindExtra` 保存为 `null`

### Requirement: 账号发现按浏览器分区复用凭证

系统 MUST 在凭证写入时按 `partitionName` 查找现有凭证；存在时复用，不存在时创建。
本地酒店记录的唯一性 MUST 继续由 OTA 渠道与酒店 ID 决定；同一凭证 MUST 允许关联多条
酒店记录。

#### Scenario: 已有分区再次发现酒店

- **WHEN** 某浏览器分区已经对应一个 `OtaCredential`
- **AND** 该分区再次探测出酒店
- **THEN** 系统复用原凭证
- **AND** 系统将结果作为候选返回，不自动更新既有酒店记录

### Requirement: 同一登录态关联多个酒店

系统 MUST 在同一浏览器分区探测出多个 OTA 酒店时，将全部酒店作为候选返回，并 MUST NOT
选择其中任意一家酒店 ID 作为 credential 的渠道账号 ID。用户每次确认 MUST 只能选定一家
酒店；已确认的每家酒店分别由一条本地酒店记录表示并指向同一个 `credentialId`。

#### Scenario: 同一分区探测出多家酒店

- **WHEN** 同一浏览器分区发现多个 OTA 酒店
- **THEN** 系统不得选择其中任意一家酒店 ID 作为 credential 的渠道账号 ID
- **AND** 系统将全部酒店作为候选返回供用户选择

#### Scenario: 用户从多个候选中选定一家

- **WHEN** 候选列表包含多家酒店
- **THEN** 用户每次确认只能选定其中一家
- **AND** 系统仅为被选定的酒店写入本地酒店记录

## REMOVED Requirements

### Requirement: 现有账号使用效果保持一致

**Reason**: 该需求描述的是 credential/account 拆分期间的行为兼容性保证，其中「返回已按新模型发现并保存的账号集合」以「发现即保存」为前提。新语义下未确认的探测结果不再进入持久化集合，该保证的表述已不成立。列表读取行为由「本地只保存酒店信息，不表达绑定关系」覆盖。

**Migration**: 列出某渠道的酒店时改为读取本地酒店记录（用户已确认保存的酒店），而非探测结果集合。每条结果仍包含关联 credential 的标识。
