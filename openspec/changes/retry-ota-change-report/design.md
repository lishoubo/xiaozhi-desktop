## Context

`AmountChangeReportService` 原本在任何 gateway 异常后立即重试一次。`createRmsApiCall` 会把网络、HTTP 与业务失败都抛成普通错误，上报层无法分辨是否值得重试。`createAuthenticatedRmsFetch` 已单独处理一次 401 令牌刷新；这与上报层的瞬时故障重试职责不同。上报体已有稳定的 `operationId`。

## Goals / Non-Goals

**Goals:** 在上报服务保留一个有上限的重试点，按明确的可恢复性区分错误，并复用原上报体。

**Non-Goals:** 不新增离线队列、全局重试器或 RMS 服务端改动；不改变认证层的 401 处理。

## Decisions

1. 用 `1_000`、`3_000` 毫秒两段固定等待，最多三次发送。只在失败后等待；首次成功不增加延迟。该低频、单条上报链路用固定短延迟满足用户要求，暂不引入随机抖动。若将来出现批量同步重试，再评估 jitter 与总重试预算。
2. RMS HTTP 拆包层为抛出的错误携带可重试标记：网络传输失败、HTTP 408/429/5xx 为可重试；其余 HTTP 4xx、正常 HTTP 响应中的业务码拒绝及非可重试响应形状错误为永久失败。上报服务只依据这一窄标记决定是否等待与重发。这样避免从错误文案猜状态，也避免改变其他 gateway 的调用语义。
3. 所有尝试复用同一 report 对象和 `operationId`。业务处理终态 `code=0` 仍由 gateway 视为已接收，不再上报层重试。
4. 保持现有单向通知语义：最终失败记结构化告警，不向 watcher 抛出。认证层 401 刷新仍在下层运行，上报层不会对最终 401 再重试。

## Risks / Trade-offs

- [网络请求一直不返回] → 本变更不新增超时；重试只能在请求明确失败后开始，后续可独立设定单次请求超时。
- [多个客户端同时遇到故障] → 两次固定等待可能同步；上限为两次且链路低频，先保持实现简单。
- [服务端已收下报文但响应丢失] → 同一 `operationId` 供下游去重，不为每次重试生成新键。

## Migration Plan

无需数据迁移。随 desktop 版本发布；回退为原两次尝试的实现即可。
