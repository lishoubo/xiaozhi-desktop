## Why

用户从酒店管理页选择已有美团账号重新登录时，标签页会先打开一个被判为“已登录”的工作台 URL；失效会话随后可能跳到美团登录页。现有发现脚本仍会遍历 `globalStorage` 的所有历史候选并逐个请求账号详情，无法区分当前登录账号与旧缓存，请求也没有超时。客户反馈在登录页连续出现“账号异常”原生弹窗；目前只能确认这条探测链路具备触发条件，尚不能把弹窗归因于某个具体请求。

## What Changes

- 对从已有美团凭证打开的标签页，使用该凭证的渠道账号 ID 作为唯一待验证账号；本地 `credentialId` 只用于定位凭证，不直接传给美团接口。
- 对没有可用渠道账号 ID 的新登录或老数据路径，先确认当前页面已有有效登录身份；历史缓存中的多个 ID 不再被逐个当成当前账号试探。身份无法唯一确认时保持待登录/待重试状态，不写入凭证或宣称重登成功。
- 给美团身份请求设置有限时和取消条件，并记录不含账号值、请求正文或凭证的结构化阶段日志，以区分“未登录”“身份不明”“请求超时”和“已确认”。
- 保持绑定、重登、普通打开及账号切换的业务核对边界；确认身份后才进入现有门店探测或重登结果分发。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `local-ota-credentials`: 美团凭证发现必须依据当前有效登录态核验账号身份；已有账号定向验证，无已知账号时不得遍历历史缓存猜测身份。

## Impact

涉及 desktop 的 OTA 标签意图、登录判定、美团身份发现和相应定向测试；如需传递“预期渠道账号 ID”，调整 desktop 内部类型和调用链。无 server API 或数据库迁移。实现前须用可复现样本验证美团登录成功信号与请求方式，避免以 URL 或缓存存在替代真实登录态。
