## Context

见 `proposal.md`。酒店管理页选中的 `credentialId` 是本地 SQLite 凭证主键；对应记录的 `channelAccountId` 才是美团 `bizAcctId`。账号锚点和酒店锚点的美团重登都经 `ReauthDialog → openExisting → LoginDetector → OtaCredentialService → meituan/discovery`。`openExisting` 总是加载 `/ebooking/merchant/ebIframe`，该路径命中现有 URL 判据；失效会话跳到登录页前，发现动作可能已经开始。`globalStorage` 可保留多个历史候选，不能证明当前登录身份。`OtaCredentialService.bound` 在同一进程内还会把已有凭证直接作为“已发现”结果返回。

## Goals / Non-Goals

**Goals:** 让已有美团账号定向核验、无 ID 的登录按当前会话发现身份；失效和超时不能向下游交付旧身份；保留账号锚点、酒店锚点和绑定的既有核对语义。

**Non-Goals:** 不拦截或隐藏美团自己的弹窗；不更改其他渠道的登录发现；不更改扫描任务或 RMS 接口；不凭本地 `credentialId` 推断美团账号身份。

## Decisions

### 1. 已有账号的 ID 在主进程解析，作为发现提示传递

`openExisting(credentialId, intent)` 已读取完整 `OtaCredential`。它把非空的 `channelAccountId` 作为该 tab 的 `expectedChannelAccountId` 交给 `LoginDetector`，再传到美团发现函数；`credentialId` 不进入美团请求。新登录 tab 没有提示，历史凭证 ID 为空也没有提示。该提示约束本次定向核验的请求对象，但**不是登录成功证明**，更不能直接回传 repository 中的旧凭证。

普通打开已有账号、绑定和重登共用这个提示来源；重登 `reauth-ota` 的现有 expected ID 核对继续保留，`reauth-by-hotel` 的门店核对继续保留。**重登本次只验证所选 ID**，用户实际切成另一个账号时返回身份不符，不向其他历史 ID 继续探测。普通打开已有账号后若用户主动切换账号，只有观察到新的登录状态与新鲜、唯一的当前账号线索，才能另起一次发现并沿用现有 partition 归并逻辑。没有可靠线索时返回身份未确定，不把旧 ID 当作当前身份。

普通标签首次核验旧账号失败后，即使跳到登录页也保留所选 ID；用户重新登录同一账号仍走定向核验。只有该 tab 已成功确认过身份、之后又进入登录页，普通打开才切到“新账号线索”模式。每次成功识别后刷新历史线索基线；历史候选间来回切换但没有新线索时仍返回身份未确定，用户可从账号列表重新打开目标账号做定向核验。

### 2. 先用独立于网页 JS 的同 partition 请求确认会话

美团身份发现改为由主进程通过该 tab 的 Electron session 发同 partition 的 `getDetail` 请求（有 ID）或 `poiInfos` 请求（无 ID 的会话预检）。沿用已验证的固定请求头和响应 schema；预检只接受 HTTP 成功且业务成功码，`getDetail` 还须校验 `bizAcctId` 与请求 ID 相同。当前 URL 必须仍是受信任的美团 HTTPS 主 frame。**URL 命中只表示可以尝试预检，不表示已登录。**预检失败时不执行任何页面内账号详情 XHR，也不继续酒店探测。

选择主进程请求是为了让失效响应不经过网页可能安装的 XHR 拦截器。现有踩点记录表明同 partition Cookie 加固定头足以访问 `getDetail`，但尚未实测 `session.fetch`；实现任务的第一步需在有效与过期美团会话各验证一次。若有效会话无法通过该请求方式，不能回退到失效时仍会在页面执行的旧候选遍历；须先调整可行的安全请求方式并更新设计。

### 3. 无 ID 时只接受可归因于本次登录的唯一候选

预检确认会话有效后，页面脚本只读取账号线索，不发 `getDetail`。新 partition 登录后首次出现的唯一 `bizAccountId` 可作为候选；旧 partition 必须能观察到从登录页到已登录页的状态转移以及对应的新鲜、唯一候选。若只有无法判新旧的历史缓存，或同时存在多个候选，就返回 `identity-unavailable`，不“挨个试到成功”。随后对唯一候选通过主进程请求 `getDetail`，复用现有白名单解析与持久化。

这会让少数历史缓存混杂的老账号需要用户重新登录到新 partition；这是宁可延迟恢复也不误认账号的取舍。页面没有进入有效登录态时，等待后续导航/登录动作触发下一次判定，而不是定时循环请求。

旧 partition 无 ID 的基线可在首次登录前的 `/ebooking/` 页面或首次可见的同源登录页读取。若登录页读取失败，不能在登录后的页面把新线索倒记为“旧基线”；此时返回身份未确定。初始 `/ebooking/` 上的失效响应保持为“等待登录”，不提前消费重登请求的 `requestId`。

### 4. 会话验证不得被进程内 `bound` 缓存绕过

美团显式打开标签的发现结果必须来自本次有效会话；不得走 `bound` 的旧凭证早退，已有的 `inflight` 才负责合并并发工作。每 tab 同时最多一次身份发现；失败后仅在新的导航/登录状态变化时重试。请求设有限时并在 tab 关闭或回到登录页时取消；无法及时取消的结果以 tab 的导航代次作废，不写库、不向下游广播“已核验”。酒店探测和重登分发仍只在身份成功持久化之后运行。

### 5. 诊断信息记录阶段，不记录账号内容

记录 `tabId`、`requestId`（若有）、发现模式（定向/无 ID）、阶段、结果类别和耗时；不记录渠道账号 ID、URL 查询串、Cookie、原始响应或弹窗正文。保留原生弹窗观察日志，以便实测比较“预检失败/取消”与弹窗发生时间。

## Risks / Trade-offs

- [主进程 `session.fetch` 与页面请求行为不同] → 首个实施任务验证有效、失效两类会话；有效会话不通过时暂停编码，先重新确定安全传输方式。
- [美团接口对非当前账号也返回详情] → `bizAcctId` 匹配仅证明所查账号，不能单独证明当前登录者；无 ID 路径还要求本次登录产生的唯一线索，重登继续执行原账号/酒店锚点核对。
- [历史缓存无法唯一归因] → 返回可恢复的身份未确定状态，保留原绑定和凭证；明确引导用户完成新登录。
- [会话在请求期间跳转或 tab 关闭] → 有限时、取消和导航代次校验共同阻止迟到结果落库。
- [现有进程内缓存优化被收紧] → 美团显式打开可能多一次轻量身份请求，以正确性换取请求成本；同 tab 并发仍去重。

## Migration Plan

无数据迁移或服务端发布。先做有效/失效会话请求验证，再按 desktop 内部链路接入 ID 提示、预检、超时及取消。定向回归覆盖失效旧账号停留登录页、手动登录恢复、无 ID 新登录、多历史候选、同 partition 已缓存身份、切换账号和两种重登锚点；发布前用 Windows 诊断包复核弹窗次数与阶段日志。回滚为上一桌面版本，不改动数据库结构。
