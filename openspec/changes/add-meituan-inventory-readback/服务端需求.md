# 服务端需求：美团房量回读上报（inventoryReadback）

> 面向 rms-server。desktop 侧已实现，本文档是接入所需的全部信息。
>
> 姊妹文档：`add-ctrip-inventory-readback/服务端需求.md`（携程）。两条上报**外层同构**，
> 差异只在 `changeRaw.cells` 的字段名 —— 若携程那条已接，本条的工作量主要是 cells 的映射。

---

## 1. 背景：这条上报解决什么

美团房量的「增加 / 减少」是**相对操作**，写请求只说增量不说基数：

| 操作 | `countType` | `limitChangeValue` | `count` |
|---|---|---|---|
| 设为某值 | `1520` | 目标值 | 0 |
| **增加** | `1620` | 增量 | 0 |
| **减少** | `1720` | 减量 | 0 |
| 设为不限 | `1920` | 0 | 0 |
| 设值 + 预留房 | `1525` | 房量 | 预留房数 |
| 纯房态操作 | `1020` | 0 | 0 |

> 上表由 desktop 踩点整理，**仅供参考** —— 回读链路不解码 `countType`，服务端若要用请自行核实。

而写接口**不回传改后状态**。所以「渠道现在到底是多少房量」算不出来。

这也正是既有 `MeituanInventoryUpdateTranslator` **刻意只采房态不采房量**的原因（那个类注释写得很清楚：当时样本里三个房量字段恒定不变，无法推断语义，而猜错会把「房态操作」变成「把房量改成 0」）。

本上报补的就是这块：改完之后主动读回渠道的真实状态。

```
上报 A  changeType=roomStatus        changeRaw = 写请求报文        ← 用户想改成什么
上报 B  changeType=inventoryReadback changeRaw = { trigger, cells } ← 实际是什么
```

---

## 2. 接入方式

**复用现有端点 `POST /api/v1/app/ota-changes`，报文结构不变。**

`AppChangeTranslatorRegistry` 按 `(source, endpointId)` 分派，Translator 由 Spring 注入
`List<AppChangeTranslator>` —— 新增一个 `@Component` 即可，注册表本身不用改。

分派键：

| 字段 | 值 |
|---|---|
| `source` | `MEITUAN` |
| `endpointId` | `queryRoomStatusInfo` |
| `changeType` | `inventoryReadback`（与携程同值，服务端只进日志，不参与分派） |

> ⚠️ `endpointId` 用的是**回读接口**的名字，不是触发它的写端点。后者
> （`inventory-update`）已被 `MeituanInventoryUpdateTranslator` 认领
> （`supports("MEITUAN", "inventory-update")`），复用会让回读体被按写报文的形状解析。

**在服务端 Translator 上线前**，这些报文会落 `raw_body` 并返回 `UNKNOWN_ENDPOINT`，数据不丢。
desktop 可以先上线。

## 3. 报文结构

顶层字段与既有上报完全一致，差异全在 `changeRaw`：

```json
{
  "source": "meituan",
  "changeType": "inventoryReadback",
  "endpointId": "queryRoomStatusInfo",
  "endpointUrl": "https://me.meituan.com/api/gw/v1/product/goods/queryRoomStatusInfo",
  "otaHotelId": "<凭证的 masterHotelId，service 层填>",
  "operationId": "<独立生成>",
  "submitAt": "2026-09-18T10:00:01.000Z",
  "changeRaw": {
    "trigger": {
      "endpointId": "inventory-update",
      "observedAt": "2026-09-18T10:00:00.000Z",
      "rawRequest": { "poiId": "1834077877", "partnerId": 4824962,
                      "modifyInventoryModelList": [ … ] }
    },
    "probedAt": "2026-09-18T10:00:01.000Z",
    "truncated": false,
    "cells": [
      { "roomId": 493882496, "roomName": "云享三人间", "roomCategory": 1,
        "containerId": 372062584, "date": "2026-09-19",
        "roomStatus": 1, "limitType": 1, "remainCount": 1,
        "limitRemain": 5, "usedCount": 0, "invSwitch": 1, "shareType": 1 }
    ]
  }
}
```

### 3.1 `changeRaw.trigger` —— 这次回读是谁触发的

| 字段 | 含义 |
|---|---|
| `endpointId` | 触发本次回读的写端点，**恒为 `inventory-update`** |
| `observedAt` | 观测到写请求的时刻 |
| `rawRequest` | 那次写请求的报文，**与上报 A 的 `changeRaw` 是同一份** |

`rawRequest` 的结构见既有 `MeituanInventoryUpdateTranslator` 的类注释，此处不重复。

### 3.2 `changeRaw.cells` —— 回读到的事实

每个元素 = 一个 (房型, 日期) 格子。字段**原样透传**美团响应，desktop 只并入了
`roomId` / `roomName` / `roomCategory` 三个来自 `roomBaseInfo` 的字段，以及以 map key 为准的 `date`。

| 字段 | 说明 |
|---|---|
| `roomId` | ⚠️ **物理房型** id，不是售卖房型 —— 与既有 `inventory-update` 上报一致，下游认的 `goodsId` 需查库展开，1:多 |
| `roomName` | 房型名，便于排查 |
| `roomCategory` | 恒为 `1`（日历房）—— desktop 已过滤，见 §4.2 |
| `date` | `YYYY-MM-DD` |
| `roomStatus` / `invSwitch` | 房态相关 |
| `limitType` | `1` = 限量，`2` = 不限量 |
| `remainCount` / `limitRemain` / `usedCount` | 房量相关，⚠️ **语义待确认**，见 §4.1 |
| `containerId` / `shareType` | 美团内部标识，原样带上 |

> ⚠️ 美团可能随时加字段。desktop **不做白名单**，整行透传，服务端按需取。

## 4. ⚠️ 四条反直觉约定（务必读）

### 4.1 房量字段：`limitRemain` 是用户设置的那个值（真机实证，建议复核）

一格里有三个数字都像房量。**2026-09-18 真机实测**给出了强证据：

| # | 用户操作 | 写请求 | 回读 `limitRemain` |
|---|---|---|---|
| 1 | 房量 +1（用户确认结果是 19） | `countType:1620, limitChangeValue:1` | **19** ✅ |
| 2 | 周末设 19 / 平时设 17 | `countType:1520`，两档 19 / 17 | 10-23(周五) **19**、10-22(周四) **17** ✅ |

⚠️ 第 1 组尤其关键：写报文里**只有"+1"，没有任何地方出现 19** —— 绝对值只能由回读得到。
这正是本链路的立论。

两组覆盖了**两种不同的写操作路径**（相对 `1620` 与绝对 `1520`），都指向同一字段。

同一格里 `remainCount` 恒为 1、`usedCount` 恒为 0，与 `limitRemain` 显然不同语义
（推测 `remainCount`=物理剩余、`usedCount`=已售，**未实证**）。

> **建议服务端用镜像数据复核边界情况**：上述两组都是「无预留房、`usedCount:0`、
> `limitType:1`」的干净场景。有已售或有预留房时三个字段如何分配，尚无样本。

⚠️ `limitType: 2`（不限量）时 `limitRemain` 是 **998/999 这类哨兵值**，不是真实房量。
仅凭数字判「还剩几间」会把不限量的房型判成快满房 —— 与携程
「`limitSale:"F"` 时房量 0 不代表没房」是同一类陷阱。**先看 `limitType`，再读数字。**

**desktop 侧仍然整行透传、不判读** —— 上述结论写在文档里供服务端采用，但
desktop 代码中**不会**出现「取 `limitRemain` 当房量」这类分支。这是 change 的硬约束：
客户端一旦开始解读语义，美团改字段时就会静默错报。

### 4.2 `cells` 只含**日历房**，已按 `roomCategory === 1` 过滤

美团回读接口对**同一个 `roomId` 会返回两行**，靠 `roomCategory` 区分，房量完全独立：

```
roomId 493879575  roomCategory 1(日租)  containerId 372062583  limitType 1  limitRemain 1
roomId 493879575  roomCategory 2(钟点)  containerId 392353398  limitType 2  limitRemain 999
```

实证：踩点的「钟点房设置房量」样本用 `hourRoomIdList:[493879575]`，与日租那条的 roomId
**完全相同** —— 同一 id 兼具两副身份。

desktop 只上报 `roomCategory === 1` 的行，与既有 `MeituanInventoryUpdateTranslator`
「只跟日历房」同口径。**钟点房的改动完全不触发回读。**

### 4.3 `cells` 的日期范围**已经是精确范围**

desktop 侧已把日期区间与星期筛选取过交集，`cells` 里的日期**恰好**是用户本次改动实际
影响的那些天。

⚠️ **不要再拿 `rawRequest.modifyDates` 去展开** —— 用户只勾了周五六时那可能是 30 天，
会比实际多跟 20 多天。要跟价直接用 `cells[].date`。

⚠️ `rawRequest` 里的 `modifyParamByEffectWeeks[].effectWeek` 是 **ISO 星期，1 = 周一**，
与服务端既有的 `RawBodyReader.weekdaysFromInts` + `AppOtaChangeIngestService.toDayOfWeek`
（`DayOfWeek.of(v)`）同口径 —— desktop 是照着服务端这个实现对齐的。

### 4.4 `truncated` 恒为 `false`

携程有「应用到所有日期」选项（会改从今日起约两年，客户端算不出范围，只能裁剪窗口并标记
`truncated`）。**美团没有这个选项**，回读范围总是精确的。

字段保留纯为与携程上报体同构，服务端可以一套逻辑处理两个渠道。

---

## 5. `operationId` 独立，不可互相去重

一次用户改动会产生**两条**上报，携带**不同的** `operationId`：

| | changeType | endpointId | 内容 |
|---|---|---|---|
| 上报 A | `roomStatus` | `inventory-update` | 用户想改成什么（写请求报文） |
| 上报 B | `inventoryReadback` | `queryRoomStatusInfo` | 实际变成了什么（回读结果） |

⛔ **两者是两个独立事实，不可互相去重。** 把 B 当成 A 的重复而丢弃，就失去了本需求的全部价值。

## 6. 其他须知

- **只有渠道判定成功的改动才会触发回读** —— 渠道拒绝的改动不会产生上报 B。
- **纯房态操作也会产生上报 B**（`countType: 1020`）：读回的房量正是「没变」这一事实，同样有效。
  desktop 刻意不按 `countType` 猜「这次改的是不是房量」—— 那个判断的失效方式是静默漏报。
- **`cells` 可能为空**（成功但这些天确实没数据），这与失败是**不同**的情况。
- **偶发漏报是已知取舍**：回读失败不重试、不落盘。所以「有 A 无 B」是正常情况，**不该按错误告警**。
- **✅ 美团写入是同步的**，不存在携程「可能读到改动前的值」那个问题 —— 携程文档 §6 的那条警告
  **不适用于美团**。

## 7. 当前状态

desktop 侧实现完成，单测 49 项通过，关键判据已做反向验证（星期基准、`roomCategory` 过滤、
日期集合过滤、空值护栏四条各自改坏后测试均变红，且红的用例数各不相同）。

### ✅ 真机验证通过（2026-09-18，门店 1834077877）

| 场景 | 操作 | 结果 |
|---|---|---|
| 单日相对改动 | 房型 493899418，10-22 房量 +1 | `limitRemain: 19`，109ms |
| **星期分档** | 10-22~10-23，周末 19 / 平时 17 | 10-22(周四) **17**、10-23(周五) **19** |
| **批量多房型** | 2 房型 × 10-22 各设 18 | 两格均 `limitRemain: 18`，**一次请求**，120ms |
| **钟点房** | `hourRoomIdList` 设 11 | `skipped: no-targets`，**一个回读请求都没发** |

**星期分档那条尤其有价值**，它一次性证实了四件事：

- `effectWeek` 是 **ISO，1=周一** —— 10-23 是周五，落进 `[5,6]` 拿到 19。
  若基准是「1=周日」，周五会被算成 `6` 之外而拿到 17，数字会**反过来**。
- 美团「周末」按酒店业口径是**周五周六**（`[5,6]`），与携程 `"0000110"` 同解。
- 多星期档取并集 → `dateCount: 2`，两天都读到。
- 按目标日期集合精确过滤 → `cellCount: 2`，不多不少。

### 一次改动 = 一条回读上报，不按房型拆

批量场景实测：用户一次改 2 个房型，desktop **只发一个回读请求**
（`roomIds: [a, b]`，接口本身支持数组），产出**一条**上报，两个房型在同一个 `cells` 里。

```
Amount change observed          ← 一次观测
Reporting amount change         ← 上报 A（写报文）
readback finished cellCount:2   ← 一次回读
Reporting amount change         ← 上报 B（回读结果，含 2 格）
```

⚠️ 未验证房型数量上限（实测最多 2 个）。若将来出现「一次改几十个房型」的场景，
需确认接口是否有上限。

> 同一 `roomId` 可能在不同操作里以日租 / 钟点两副身份出现（实测 493879575 两者都有），
> 靠写报文的 `dayRoomIdList` / `hourRoomIdList` 区分，回读侧再按 `roomCategory` 复核。
