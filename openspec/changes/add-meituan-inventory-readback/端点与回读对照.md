# 美团上报速查 —— 服务端对照表

desktop 会给服务端发哪几种上报、各自怎么认、`changeRaw` 里是什么。

---

## 一、全部上报类型

| `changeType` | `endpointId` | 用户做了什么 | `changeRaw` 是什么 |
|---|---|---|---|
| `roomStatus` | `inventory-update` | 改房量（可同时改房态） | 写请求报文，原样 |
| `roomStatus` | `inventory-status-switch` | 单独**开**房 | 写请求报文，原样 |
| `roomStatus` | `inventory-roomstatus-submitaudit` | 单独**关**房（走审核） | 写请求报文，原样 |
| `price` | `calcPriceV2` | 改价 | 试算结果（不是提交体） |
| `inventoryReadback` | `queryRoomStatusInfo` | （改房量后自动回读） | `{ trigger, cells }` |
| `inventoryDiff` | `inventoryScan` | ⚠️ **没人操作，渠道自己变了** | `{ probedAt, cells }` |

**认一条上报只看 `endpointId`**，它唯一确定了上面六行中的一行。

⚠️ 最后一行（定时扫描）与前五行**性质不同**：前五行都跟在用户操作后面，它是定时器
主动发现的。规格见 `add-meituan-inventory-scan/服务端需求.md`。

---

## 二、⚠️ 三个坑

### 1. `changeType` 不能用来区分改房量 / 改房态

三个量态端点的 `changeType` **全是 `roomStatus`**，包括改房量那个。它只是「量态类」的
粗标记。要区分实际改了什么，看 `endpointId`，或读 `changeRaw` 里的
`countType`（房量）/ `invSwitch`（房态）。

### 2. 一次改房量发**两条**上报，B 覆盖 A

```
A  roomStatus        + inventory-update      → 触发器，内容是「+1」这类相对操作
B  inventoryReadback + queryRoomStatusInfo   → A 触发的回读，内容是绝对值
```

B 的 `trigger.rawRequest` **完整包含 A 的报文**，所以这条路上 **A 的信息量是 B 的子集**，
判「改成了什么」只认 B 即可。

两条 `operationId` 不同（各自独立生成）——⚠️ 指的是**别当成重复上报丢掉一条**，
不是说两条都得算一次改动。

### 3. ⚠️ 但**不能**简化成「只处理 `inventoryReadback`」

单独开/关房**没有 B 条**，只有 A：

| `endpointId` | 有 B 吗 | 服务端拿什么 |
|---|---|---|
| `inventory-update` | ✅ | 可以只看 B |
| `inventory-status-switch`（开房） | ❌ | **只能看 A** |
| `inventory-roomstatus-submitaudit`（关房） | ❌ | **只能看 A** |

原因：后两者的报文里只有单个 `roomId`、没有房型集合，还原不出回读入参。

---

## 三、单独说明

### `price` 的 `endpointId` 是试算端点

用户点的是提交（`updatePriceV2`），但上报内容取自**试算**（`calcPriceV2`）——
提交体只有相对操作，对 RMS 是死信息。所以 `endpointId` / `endpointUrl` / `changeRaw`
一致指向试算那次。

### 关房只代表**提交了申请**

`submitaudit` 要走美团审核，拦到上报 ≠ 房态已关上。对时效敏感的话要考虑这层延迟。

### ⚠️ `inventoryReadback` 的 `otaHotelId` 是空串（desktop 已知缺陷）

`roomStatus` 那条带门店 ID，`inventoryReadback` 那条是 `''`。desktop 侧待修，
服务端按门店反查时注意。

### ⚠️ `change_type` 列宽要 ≥ 17

`"inventoryReadback"` 是 17 字符，当前 `VARCHAR(16)` 装不下，insert 直接抛
`DataIntegrityViolationException` → 500，**数据 100% 丢失**。

```sql
ALTER TABLE app_ota_change_target MODIFY COLUMN change_type VARCHAR(32);
```

## 四、`changeRaw` 的形状

### `inventoryDiff`（定时扫描）

```json
{
  "probedAt": "2026-09-22T02:00:03.000Z",
  "cells": [
    { "itemType": "roomStatus", "roomId": 354223342, "date": "2026-09-22",
      "roomStatus": 1, "limitRemain": 5, "usedCount": 0, "invSwitch": 1 },
    { "itemType": "price", "goodsId": 847226645, "date": "2026-09-22",
      "salePrice": "20700", "basePrice": "18009", "subRatio": 1300 }
  ]
}
```

⚠️ **与回读的 cells 形状不同**，两处差异：

```
inventoryReadback   { trigger, probedAt, truncated, cells }   cells 只有房态房量
inventoryDiff       { probedAt, cells }                       cells 含两类，带 itemType
```

⭐ **两个房型 ID 空间**：`itemType: 'roomStatus'` 的 cell 用 `roomId`（物理房型），
`itemType: 'price'` 的用 `goodsId`（售卖商品 = `ota_sale_room_type_id`）。
**按 `itemType` 分派，不要靠字段特征猜。**

⚠️ 金额是「分」的**字符串**；`limitRemain` 是「配额 − 已售」不是配额本身。

### `inventoryReadback`

```json
{
  "trigger": { "endpointId": "inventory-update", "observedAt": "...", "rawRequest": {...} },
  "probedAt": "...",
  "truncated": false,
  "cells": [
    { "roomId": 493882496, "roomName": "云享三人间", "roomCategory": 1,
      "date": "2026-09-19", "roomStatus": 1, "limitType": 1,
      "remainCount": 1, "limitRemain": 5, "usedCount": 0, "invSwitch": 1 }
  ]
}
```

`cells` 已按日历房（`roomCategory: 1`）过滤、按用户实际改动的日期集合过滤。
字段语义见 `inventory-readback-payload.ts`。

⚠️ `limitRemain` = 配额 − 已售，**不是**用户设的配额本身。

### `roomStatus` / `price`

原样透传写请求 / 试算结果，规格分别见 `amount-change-payload.ts`、`room-close-payload.ts`。

## 五、已知覆盖缺口

**单房态房量页**的 `inventory/update` 发的是另一种报文形状
（`separateOperateInvDateList[]`，注意 `modifyParamByEffectWeek` 是单数），
desktop 与服务端 `MeituanInventoryUpdateTranslator` 都只认
`unifiedOperateInvDateModel` —— 该页面**既没有 A 条也没有 B 条**。

既有缺口，不是回读引入的。房价房量日历页与批量改房态房量页均不受影响（已真机验证）。
