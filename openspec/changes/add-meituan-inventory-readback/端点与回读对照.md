# 美团操作入口、上报与回读 —— 服务端对照表

供服务端简化美团上报处理时使用：先看用户操作是否已经上报，再看是否另有回读上报，
最后决定用户操作上报是否还要参与业务处理。下表的端点名**全是上报里的 `endpointId`**。

---

## 一、用户操作上报与回读上报：服务端该处理哪条

| 用户操作 | 用户操作是否上报？`endpointId` | 操作后是否另发回读？`endpointId` | 服务端处理建议 |
|---|---|---|---|
| 房价房量日历页：修改弹窗里改房量，或同时改房态 | **是**，`inventory-update` | **是**，`queryRoomStatusInfo` | **收到回读时可只用回读处理改后量态**；用户操作上报不再重复处理量态 |
| 房价房量日历页：修改弹窗里**只改房态** | **是**，`inventory-update` | **是**，`queryRoomStatusInfo` | 同上；回读不按 `countType` 排除纯房态操作 |
| 批量改房态房量页 | **是**，`inventory-update` | **是**，`queryRoomStatusInfo` | 同上；多个房型合成一次回读 |
| 单房态房量页：**直接开房** | **是**，`inventory-status-switch` | **否** | **现有服务端处理这条操作上报**，可以解释抖音跟开房；不能关掉 |
| 单房态房量页：**直接关房** | **是**，`inventory-roomstatus-submitaudit` | **否** | **现有服务端处理这条操作上报**，可以解释抖音跟关房；不能关掉 |
| 单房态房量页：**修改房量** | **是**，`inventory-update` | **进入同一条回读链路**；只有请求中存在 `unifiedOperateInvDateModel.modifyDates`，且提取出日历房与日期，才会实际查询并上报；代码没有处理 `separateOperateInvDateList` | **服务端以收到的回读上报为准**；不能仅凭页面名称认定这次有回读 |
| 房价房量日历页：**直接开房** | **是**，`inventory-status-switch` | **否** | **现有服务端处理用户操作上报**；不能关掉 |
| 房价房量日历页：**直接关房** | **是**，`inventory-roomstatus-submitaudit` | **否** | **现有服务端处理用户操作上报**；不能关掉 |
| 改价 | **是**，`calcPriceV2` | **否** | **必须处理改价上报**；这里的 `calcPriceV2` 是上报的 `endpointId`，内容取自试算结果 |

这里的**“单房态房量页”**来自踩点文件 `docs/踩点/美团/单房态房量01.md`：
页面地址是 `https://me.meituan.com/ebooking/merchant/product#/index`，指在商品管理
首页针对**一个房型**编辑日期房态/房量的操作；它不是“房价房量日历页的修改弹窗”，
也不是“批量改房态房量页”。**这个页面至少有两种独立处理链路**：直接开/关房
走房态端点，由现有服务端处理操作上报；修改房量走 `inventory-update`。旧踩点
记录的请求把日期放在 `separateOperateInvDateList[]`（每段日期自带
`modifyParamByEffectWeek`）。
房价房量日历页修改弹窗和批量页的 `inventory-update` 则使用 `unifiedOperateInvDateModel`。
早期踩点把开、关两次请求都记成 `inventory/status/switch`；后续真机联调和当前
desktop / 服务端代码确认关房使用 `inventory/roomstatus/submitaudit`。

**监听不是按这几行页面分别实现的。** `AmountChangeWatcher` 对美团标签页检查 URL；
`isWatchableUrl` 接受 `me.meituan.com` 下 pathname 以
`/ebooking/merchant/product` 开头的页面，忽略 hash。因此商品首页 `#/index`、
批量房态房量页 `/ebooking/merchant/product/batch-inventory`，以及这个前缀下的
房价房量日历入口，都会挂**同一个** `AmountSaveCapture`。它按网络请求路径拦截
`/api/gw/v1/product/goods/inventory/update`，与请求来自哪个子页面无关。
该请求成功后统一产出操作上报并调用回读调度；是否真正读到数据，再由请求体形状决定。

**这里“进入回读链路”和“回读上报”是两步。** 代码先从写请求中找出
“哪个房型、哪几天被改了”，再调用美团 `queryRoomStatusInfo` 读取最新值，
最后向服务端发送 `endpointId=queryRoomStatusInfo` 的回读上报。目标提取代码只读取
`unifiedOperateInvDateModel.modifyDates`，**没有读取 `separateOperateInvDateList` 的分支**。
如果拿不到房型或日期，就返回 `skipped: no-targets`，不会调用查询接口，也不会有回读上报。
这条判断仅由请求字段决定，代码没有按页面分支。

前三行各有**两条**上报：用户操作上报的 `changeType` 是 `roomStatus`，内容是写请求；
回读上报的 `changeType` 是 `inventoryReadback`，内容含写请求副本和操作后的实际房态房量。
因此**回读已经收到并带有目标格子时**，服务端计算改后量态可以只处理回读，
无需再把那条用户操作上报算作第二次改动。两条上报的 `operationId` 不同，
不能靠 `operationId` 相等来认作重复；回读的 `trigger.rawRequest` 是对应写请求的副本。

**不能直接停掉所有 `roomStatus` 用户操作上报的处理。** 两个页面上的直接开房、
直接关房都没有操作后回读，现有服务端依赖这两种操作上报跟随。单房态房量页的
`inventory-update` 是按**报文形状**区分覆盖范围的端点：桌面端会报写请求，且
**统一调用回读调度**。`unifiedOperateInvDateModel` 会提取目标并查询；旧的单房页面
踩点样本使用 `separateOperateInvDateList[]`，在目标提取阶段返回 `no-targets`，
不会请求 `queryRoomStatusInfo`，也不会发回读上报。当前服务端的
`MeituanInventoryUpdateTranslator` 只认 `unifiedOperateInvDateModel`，读到旧样本的
`separateOperateInvDateList[]` 会在解析阶段跳过。若启用回读链路，服务端下发开关还会
按 `endpointId=inventory-update` 统一屏蔽其操作上报。要覆盖旧样本形状的修改房量，需补回读
或补服务端解析并调整开关，不能只要求“保留处理写上报”。

**仅依赖回读还要处理缺失情况。** desktop 的回读失败不重试、不落盘，成功响应也可能返回
空 `cells`。服务端若决定对前三行不处理用户操作上报，应明确回读没到或没有目标格子时
如何处理；否则可能丢掉用户操作。这里给出的是**去重条件**，不是“每次用户操作必有回读”
的保证。

**回读读的是房态和房量，没有房价。** `queryRoomStatusInfo` 返回日历房的
`roomStatusMap`，里面有 `roomStatus`、`invSwitch`、`limitType`、`limitRemain`、
`remainCount`、`usedCount` 等字段。房价在另一接口 `queryPriceInventoryStatusInfo` 的
`goodsPriceMap`；定时扫描会读取房价，但那是独立的 `inventoryDiff` 上报，
不能当作某次用户操作的回读。

## 二、全部上报类型

| `changeType` | `endpointId` | 用户做了什么 | `changeRaw` 是什么 |
|---|---|---|---|
| `roomStatus` | `inventory-update` | 改房量（可同时改房态） | 写请求报文，原样 |
| `roomStatus` | `inventory-status-switch` | 单独**开**房 | 写请求报文，原样 |
| `roomStatus` | `inventory-roomstatus-submitaudit` | 单独**关**房（走审核） | 写请求报文，原样 |
| `price` | `calcPriceV2` | 改价 | 试算结果（不是提交体） |
| `inventoryReadback` | `queryRoomStatusInfo` | 支持的 `inventory/update` 成功后自动回读，含弹窗内纯房态操作 | `{ trigger, probedAt, truncated, cells }` |
| `inventoryDiff` | `inventoryScan` | 定时扫描发现与本地基线不同；可能是用户操作后的变化，也可能是其他渠道侧变化，不能据此判定来源 | `{ probedAt, cells }` |

**辨认上报类型看 `endpointId`**，它唯一确定了上面六行中的一行；但
`inventory-update` **不能反推出页面入口**，因为第一节前三个页面入口共用它、
报文形状可能不同。

⚠️ 最后一行（定时扫描）与前五行**触发方式不同**：它按定时器比对基线，
不绑定某次用户操作。若单房态房量页改房量后抖音跟着变化，`inventoryScan` 是
需要用上报记录核实的一条可能路径；扫描要有有效基线、发现差异，且桌面端和服务端
的扫描开关都放行，不能仅凭代码断定那次一定走了它。规格见
`add-meituan-inventory-scan/服务端需求.md`。

## 三、`changeType` 不能用来区分改房量 / 改房态

三个量态端点的 `changeType` **全是 `roomStatus`**，包括改房量那个。它只是「量态类」的
粗标记。要区分实际改了什么，看 `endpointId`，或读 `changeRaw` 里的
`countType`（房量）/ `invSwitch`（房态）。

## 四、单独说明

### `price` 的 `endpointId` 是试算端点

用户点的是提交（`updatePriceV2`），但上报内容取自**试算**（`calcPriceV2`）——
提交体只有相对操作，对 RMS 是死信息。所以 `endpointId` / `endpointUrl` / `changeRaw`
一致指向试算那次。

### 关房端点名包含 `submitaudit`

端点名本身不能证明存在审核延迟。现有服务端按关房操作处理；是否另有审核流程，
当前踩点和代码没有证实。

### `inventoryReadback` 的 `otaHotelId`

旧版曾发空串；当前 desktop 的 `buildMeituanReadbackReport` 已从触发写请求的
`poiId` 填入，服务端按实际部署版本及收到的报文核对。service 层不会替美团补这个字段。

### ⚠️ `change_type` 列宽要 ≥ 17

`"inventoryReadback"` 是 17 字符。若目标库仍是 `VARCHAR(16)`，insert 会抛
`DataIntegrityViolationException` → 500，**该条数据丢失**。上线前核对实际列宽；
以下是原服务端需求文档给出的扩宽语句，是否已执行需以目标库为准：

```sql
ALTER TABLE app_ota_change_target MODIFY COLUMN change_type VARCHAR(32);
```

## 五、`changeRaw` 的形状

### `inventoryDiff`（定时扫描）

```json
{
  "probedAt": "2026-09-22T02:00:03.000Z",
  "cells": [
    { "itemType": "roomStatus", "roomId": 354223342, "date": "2026-09-22",
      "roomStatus": 1, "limitRemain": 5, "usedCount": 0, "invSwitch": 1 },
    { "itemType": "price", "goodsId": 847226645, "date": "2026-09-22",
      "salePrice": "20700", "basePrice": "18009", "subRatio": 1300 }
  ]
}
```

⚠️ **与回读的 cells 形状不同**，两处差异：

```
inventoryReadback   { trigger, probedAt, truncated, cells }   cells 只有房态房量
inventoryDiff       { probedAt, cells }                       cells 含两类，带 itemType
```

⭐ **两个房型 ID 空间**：`itemType: 'roomStatus'` 的 cell 用 `roomId`（物理房型），
`itemType: 'price'` 的用 `goodsId`（售卖商品 = `ota_sale_room_type_id`）。
**按 `itemType` 分派，不要靠字段特征猜。**

⚠️ 金额是「分」的**字符串**；`limitRemain` 是「配额 − 已售」不是配额本身。

### `inventoryReadback`

```json
{
  "trigger": { "endpointId": "inventory-update", "observedAt": "...", "rawRequest": {...} },
  "probedAt": "...",
  "truncated": false,
  "cells": [
    { "roomId": 493882496, "roomName": "云享三人间", "roomCategory": 1,
      "date": "2026-09-19", "roomStatus": 1, "limitType": 1,
      "remainCount": 1, "limitRemain": 5, "usedCount": 0, "invSwitch": 1 }
  ]
}
```

`cells` 已按日历房（`roomCategory: 1`）过滤、按用户实际改动的日期集合过滤。
字段语义见 `inventory-readback-payload.ts`。

⚠️ `limitRemain` = 配额 − 已售，**不是**用户设的配额本身。

### `roomStatus` / `price`

原样透传写请求 / 试算结果，规格分别见 `amount-change-payload.ts`、`room-close-payload.ts`。

## 六、已知覆盖缺口

**旧踩点所记录的单房态房量页** `inventory/update` 发的是另一种报文形状
（`separateOperateInvDateList[]`，注意 `modifyParamByEffectWeek` 是单数），
desktop 的写上报解析器只要求有房型 ID，会发出**写请求上报**；上报后
`AmountChangeWatcher` 也确实会统一调用回读调度。回读目标提取器只认
`unifiedOperateInvDateModel`，因此**该踩点样本**在调度内部返回 `skipped: no-targets`：
不会发起 `queryRoomStatusInfo` 请求，也没有操作后回读上报。这是对该样本报文的
代码推导，不等于断言当前线上此页面始终发同一形状；若当前请求改为
`unifiedOperateInvDateModel`，就会走实际回读。这里说的是 desktop 主动回读链路；
没有据此断言美团网页自身完全不发读取请求。
已核对当前服务端代码：`MeituanInventoryUpdateTranslator.translate()` 对每个 model
强制读取 `unifiedOperateInvDateModel`，上述单房型请求缺少该字段时抛出解析错误，
由 `AppOtaChangeIngestService` 标成 `SKIPPED`，不会进入下发队列。服务端的
`AppChangeFollowGate` 还在回读链路开启时按端点统一屏蔽 `inventory-update`，没有
区分这两种请求形状。

这是已有的覆盖缺口，不是回读引入的。房价房量日历页的修改弹窗与批量改房态房量页
均使用 `unifiedOperateInvDateModel`，已真机验证能回读。补服务端只消费回读的逻辑之前，
必须先确认当前单房态房量页的**修改房量**实际请求形状；若仍为旧样本形状，
需决定如何获得可消费的改后状态。若要靠写上报，
还必须支持该请求形状并修正回读链路开启时的端点级屏蔽。该页的**直接开/关房**
已有独立端点和服务端处理链路，不属于这个缺口。
