## Purpose

定义桌面应用自动更新的行为契约：更新在什么时机检查、按什么判据决定某台机器是否升级、
身份或网络不可用时如何取舍，以及更新流程 MUST NOT 以何种方式影响应用的正常使用。

## ADDED Requirements

### Requirement: 仅在具备更新源的环境与平台上启动更新器

系统 MUST 在构建期确定本产物的更新源地址。更新源地址缺失时，系统 MUST 静默关闭更新
能力，MUST NOT 使构建失败，也 MUST NOT 在运行时报错——dev 与 pre 不分发给客户，没有
更新源是正常状态。

系统 MUST 仅在 Windows 上启动更新器。其他平台 MUST NOT 发起任何更新检查——macOS 的
更新替换要求新旧产物具备一致的签名身份，而本项目不做代码签名，启动更新器只会产生
必然失败的噪声。

#### Scenario: 非 Windows 平台

- **WHEN** 应用在 macOS 或 Linux 上启动并完成登录
- **THEN** 不发起更新检查
- **AND** 不产生错误日志或错误上报

#### Scenario: 环境未配置更新源

- **WHEN** dev 或 pre 环境的产物完成登录
- **THEN** 不发起更新检查
- **AND** 记录一条说明「本环境未启用自动更新」的信息级日志

#### Scenario: online 环境的 Windows 产物

- **WHEN** online 环境的 Windows 产物完成登录
- **THEN** 发起更新检查

### Requirement: 更新检查发生在身份确认之后

系统 MUST 在取得当前登录者身份之后才发起更新检查——灰度判据依赖身份，身份未知时
无法判定。

系统 MUST 覆盖所有取得身份的路径，包括用户主动登录与冷启动恢复既有会话。仅覆盖主动
登录会使「已登录用户重启应用」永远触发不到检查，而这是最常见的使用方式。

同一次应用运行内，系统 MUST NOT 重复发起更新检查。

#### Scenario: 冷启动恢复会话

- **WHEN** 已登录用户重新打开应用，会话自动恢复且未重新登录
- **THEN** 发起更新检查

#### Scenario: 一次运行内多次取得身份

- **WHEN** 同一次运行内身份被多次确认（如恢复会话后又主动刷新）
- **THEN** 只发起一次更新检查

#### Scenario: 未登录

- **WHEN** 应用启动但用户未登录
- **THEN** 不发起更新检查

### Requirement: 灰度名单决定该机器是否升级

系统 MUST 从更新源拉取一份灰度名单，并以当前登录者的手机号为判据决定是否继续更新
流程。手机号命中名单时 MUST 继续，未命中时 MUST 终止本次更新流程。

名单 MUST NOT 以明文存储手机号——更新源是可匿名读取的，明文名单等同于公开客户联系
方式。判据 MUST 基于不可逆的单向变换，且该变换 MUST 引入本应用专属的固定盐值，使
名单内容无法通过穷举常见号码段还原。

名单 MUST 支持一种表示「对全部用户开放」的形态，用于灰度观察结束后的全量放开。

#### Scenario: 手机号命中名单

- **WHEN** 当前登录者的手机号在灰度名单内
- **THEN** 继续更新流程

#### Scenario: 手机号未命中名单

- **WHEN** 当前登录者的手机号不在灰度名单内
- **THEN** 终止本次更新流程，不下载任何内容

#### Scenario: 名单已全量放开

- **WHEN** 灰度名单处于「对全部用户开放」的形态
- **THEN** 任何已登录用户都继续更新流程

#### Scenario: 名单中不含明文手机号

- **WHEN** 任何人取得灰度名单文件
- **THEN** 无法从中直接读出任何手机号

### Requirement: 身份不完整时不升级

当前登录者没有手机号时，系统 MUST 终止更新流程。服务商员工可能没有手机号，身份不足以
参与灰度判定时，保守的选择是不升级——错过一次更新的代价，远低于让名单外的机器意外升级。

#### Scenario: 登录者没有手机号

- **WHEN** 当前登录者的身份信息中手机号缺失或为空
- **THEN** 终止本次更新流程
- **AND** 记录一条说明原因的信息级日志

### Requirement: 更新失败不影响应用可用性

更新流程中的任何失败——名单拉取失败、更新源不可达、下载中断、校验不通过——MUST NOT
阻断应用启动，MUST NOT 打断用户正在进行的操作，MUST NOT 向用户弹出错误提示。

系统 MUST 记录失败原因并上报，使故障可被排查。

#### Scenario: 更新源不可达

- **WHEN** 拉取灰度名单或更新元数据时网络不可达
- **THEN** 应用照常可用
- **AND** 记录失败日志并上报
- **AND** 不向用户展示任何错误

#### Scenario: 下载中断

- **WHEN** 更新包下载过程中断
- **THEN** 应用照常可用
- **AND** 本次运行不再重试

### Requirement: 更新在用户退出应用时生效

系统 MUST 在后台完成下载，下载过程 MUST NOT 要求用户等待或确认。

下载完成后，系统 MUST 告知用户新版本已就绪，并 MUST 在用户下次退出应用时完成安装。
系统 MUST NOT 主动重启应用打断用户操作。

#### Scenario: 下载完成

- **WHEN** 更新包下载并校验完成
- **THEN** 向用户展示「新版本已就绪，重启后生效」的提示
- **AND** 不中断用户当前操作

#### Scenario: 用户退出应用

- **WHEN** 更新已就绪且用户退出应用
- **THEN** 安装新版本
- **AND** 用户下次启动时运行新版本

### Requirement: 更新只前进不回退

系统 MUST NOT 尝试将应用降级到更低版本。更新源上的版本清单被改回旧版本时，已升级的
机器 MUST 保持在当前版本，MUST NOT 触发降级。

这意味着灰度名单的作用是「阻止尚未升级的机器继续升级」，而非撤回已经发生的升级。已升级
机器的回退只能通过人工重装完成。

#### Scenario: 更新源版本号低于当前版本

- **WHEN** 更新源上的最新版本低于本机当前版本
- **THEN** 不执行任何更新动作

#### Scenario: 灰度回滚

- **WHEN** 某手机号被从灰度名单中移除，而该机器已升级到新版本
- **THEN** 该机器保持在新版本
- **AND** 不触发降级
