# 服务端需求：美团价量态定时扫描差异上报（inventoryDiff）

> 面向 rms-server。desktop 侧实现见 `openspec/changes/add-meituan-inventory-scan/`。
>
> **前置：先看携程那份**（`add-ota-inventory-scan/服务端需求.md`）—— 背景、接入方式、
> 「为什么需要主动对账」都一样，本文只讲**美团与携程的差异**。
>
> **工作量预估：新增一个 `AppChangeTranslator` 的 `@Component`，不改任何现有代码。**

## 1. 分派键

| 字段 | 取值 |
|---|---|
| `source` | **`meituan`** |
| `changeType` | `inventoryDiff`（与携程同值） |
| `endpointId` | `inventoryScan`（与携程同名） |

⚠️ **端点标识与携程同名是有意的** —— 服务端按 `(source, endpointId)` 两元组分派，
`source` 已经区分开了两个渠道。同名让「这是哪一类上报」在渠道间保持一致。

但 **`(meituan, inventoryScan)` 仍需单独写一个 Translator**：cells 的形状与携程完全不同，
见下一节。

## 2. ⭐ 与携程最大的差异：cells 里有**两个房型 ID 空间**

```
携程   房态房量 roomTypeID     价格 roomTypeID     同一空间，一套 ID 走到底
美团   房态房量 roomId(物理)   价格 goodsId(售卖)  ⚠️ 不同空间，1:多
```

```
realRoomId (物理房型)                  ← 房态、房量挂这一层
   └── goodsId A (不含早/预付)  ┐
   └── goodsId B (含早/到付)    ├─ 价格各自独立
   └── goodsId C (专享)         ┘
```

**每个 cell 自带 `itemType` 字段，据它分派：**

| `itemType` | 是什么 | 房型标识 | 对应 RMS |
|---|---|---|---|
| `roomStatus` | 房态房量 | `roomId` | 物理房型 |
| `price` | 价格 | `goodsId` | `ota_sale_room_type_id` |

⚠️ **一条上报的 `cells` 里两类混在一起**，是本轮发现的全部差异。

⚠️ **不要靠字段特征猜**（「有 `salePrice` 就是价格」）。`itemType` 就是为此而来 ——
猜错会拿 `goodsId` 去查物理房型，查不到，或更糟：查到一个同号的别的房型。

⚠️ **也不要靠 `endpointUrl` 判断**：一轮扫描打了四个端点，`endpointUrl` 只有一个位置，
填的是房态房量那个。

> 📌 携程那份上报**也已加上 `itemType`**（同一次改动，两个渠道一致）。携程两类格子
> 共用同一个 `roomTypeID`，有没有它都能定位，但字段一致能让两个 Translator 结构相同。

## 3. changeRaw 结构

```json
{
  "probedAt": "2026-09-22T02:00:03.000Z",
  "cells": [
    {
      "itemType": "roomStatus",
      "roomId": 354223342,
      "roomName": "云享三人间",
      "roomCategory": 1,
      "containerId": 372062584,
      "date": "2026-09-22",
      "roomStatus": 1,
      "limitType": 1,
      "remainCount": 1,
      "limitRemain": 5,
      "usedCount": 0,
      "invSwitch": 1,
      "shareType": 1
    },
    {
      "itemType": "price",
      "goodsId": 847226645,
      "goodsName": "云享三人间-不含早-预付",
      "date": "2026-09-22",
      "salePrice": "20700",
      "basePrice": "18009",
      "originPrice": "0",
      "subPrice": "2691",
      "subRatio": 1300
    }
  ]
}
```

`cells` 是**渠道原始行**，desktop 不解读语义、不转换枚举、不转金额单位。
除 `itemType` 外全部是美团返回的字段。

## 4. ⚠️ 五条反直觉约定

### 4.1 金额是「分」的字符串

`"20700"` = 207.00 元。**是字符串不是数字**，且单位是分。

`subPrice` = `salePrice × subRatio`，是冗余字段（desktop 也不拿它参与差异判定）。

| 字段 | 含义 |
|---|---|
| `salePrice` | 卖价（分） |
| `basePrice` | 底价（分） |
| `originPrice` | 划线价（分） |
| `subRatio` | 佣金率，**万分位**（`1300` = 13%） |

### 4.2 ⚠️ `roomStatus` 与 `invSwitch` 的语义**我们没有踩实**

两个字段都在 cell 里，但 desktop **不解读它们**（整行透传）。已知线索来自 RMS RPA 侧
（`docs/美团/RPA-房价信息.md` §12.2）：

| 字段 | RPA 侧的说法 | 我们的验证状态 |
|---|---|---|
| `roomStatus` | `1` 有房 / `0` 无房（**关房与售罄都是 0**） | ⚠️ 未自行验证 |
| `invSwitch` | 房态开关本身 | ⚠️ 未验证；写请求侧实证关房样本是 `invSwitch: 0` |

推论：**两者组合才能区分「关房」与「售罄」**

```
roomStatus 1 + invSwitch 1   开着且有房
roomStatus 0 + invSwitch 0   关房
roomStatus 0 + invSwitch 1   开着但售罄（推测）
```

⚠️ RPA 侧明说 `invSwitch`「本期不读」，所以**他们也没验过**。服务端若要据此判房态，
建议先自行核对一次。

⚠️ 两个字段都参与了 desktop 的差异判定（变了就报），这不受语义影响；
**语义解读是服务端的事**。

### 4.3 ⚠️ `limitRemain` = 配额 − 已售，**不是**用户设的配额本身

实测同一房型连续几天：

| date | limitRemain | usedCount | 用户设的配额 |
|---|---|---|---|
| 09-19 | 20 | 0 | 20 |
| 09-21 | 19 | **1** | 20 |

直接拿它当「用户设了多少房」，在有已售的日期上会**偏小**。要还原配额：
`limitRemain + usedCount`。

（这条是美团回读那次的踩坑结论 —— 当时三组真机样本的 `usedCount` 恰好全是 0，
看起来像「`limitRemain` 就是设定值」，是采样偏差。）

### 4.4 只含日历房，不含钟点房

钟点房与日历房**共用同一个 `roomId`**，但房量完全独立。desktop 在取数源头就筛掉了
（`roomBaseInfo.roomCategory === 2`）。

实测一家店 9 个逻辑房型里 **3 个是钟点房**，占三分之一 —— 不是边缘情况。

### 4.5 只含在售商品的价格

草稿、审核中、已下线的售卖商品不进入取数范围（判据 `auditStatus == 4` +
`goodsStatus == 2` + `switchStatus == 0`）—— 它们当前不对客售卖，价格变化不构成
需要跟进的渠道事实。

## 5. 门店与房型标识

| 字段 | 取值 | 说明 |
|---|---|---|
| `otaHotelId` | `poiId` | ⚠️ desktop **已填满**，不是空串 |
| cell 的 `roomId` | 物理房型 | 美团 logic 层的 `roomId`，不是 `realRoomId` |
| cell 的 `goodsId` | 售卖商品 | = RMS 台账的 `ota_sale_room_type_id` |

⚠️ **`otaHotelId` 这次是填满的**。美团回读那条上报曾经发的是**空串** —— 那是照抄携程
「留空等 service 层覆盖」的写法，而那段归一（`resolveOtaHotelId`）第一行就
`if (observed.source !== 'ctrip') return observed.otaHotelId`，**只对携程生效**。

本次已在 payload 里直接填 `poiId`，不依赖 service 层。

## 6. 美团现在有四类上报

| `changeType` | `endpointId` | 用户做了什么 | `changeRaw` |
|---|---|---|---|
| `price` | `calcPriceV2` | 改价 | 试算结果（不是提交体） |
| `roomStatus` | `inventory-update` / `inventory-status-switch` / `inventory-roomstatus-submitaudit` | 改房量 / 开房 / 关房 | 写请求报文 |
| `inventoryReadback` | `queryRoomStatusInfo` | （改房量后自动回读） | `{ trigger, cells }` |
| **`inventoryDiff`** | **`inventoryScan`** | **没人操作，渠道自己变了** | `{ probedAt, cells }` ← 本需求 |

⚠️ 前三类都跟在用户操作后面；本类**与用户操作无关**，是定时器发现的。

⚠️ `inventoryReadback` 与 `inventoryDiff` 的 `cells` **形状不同**：

```
inventoryReadback   { trigger, probedAt, truncated, cells }   cells 只有房态房量（roomId）
inventoryDiff       { probedAt, cells }                       cells 含两类，带 itemType
```

## 7. 真机实测规模（2026-09-21）

两家门店，一轮扫描的产出：

| 门店 | 在售商品 | 价格格子 | 日历房型 | 房态格子 | 合计 | 耗时 |
|---|---|---|---|---|---|---|
| 1834077877 | 18 | 270 = 18×15 | 6 | 90 = 6×15 | 360 | 748ms |
| 942804505 | 8 | 120 = 8×15 | 7 | 105 = 7×15 | 225 | 683ms |

⭐ **变更检出已验证**：在另一个浏览器改一个房型当天的房量 → 下一轮扫描
`changed: 1`，**360 个格子里精确命中那一格**，其余 359 格无误报。

⚠️ 这是**单格上报**的实例 —— 一条上报的 `cells` 里通常只有很少几个格子，
不是全量快照。

## 8. 扫描节奏

| | 值 |
|---|---|
| 间隔 | 5 分钟 + 随机抖动（dev 是 1 分钟） |
| 窗口 | 自今日起 15 天 |
| 粒度 | 逐**门店**扫描（一个美团账号挂多店，逐店各一轮） |
| 首轮 | ⚠️ **只建基线不上报** —— 没有基线的格子不算「渠道变更了」 |

⚠️ **绝大多数轮次应该零上报**。有上报才说明真的检测到了变更。

## 9. desktop 侧的已知限制

- **门店清单在登录时记录**：逐店取数需要门店级 `partnerId`，它随登录探测写入本地凭证。
  本功能上线前登录的账号需要重新登录一次才会有 —— 那之前不扫
- **一个账号失效不影响其余账号**：逐个凭证独立处理，逐门店独立处理
- **价格与房态单边失败时仍报另一边**：两类是独立事实。⚠️ 真机踩到过一次价格取数失败
  （只有房态格子上报），所以**收到一条只含 `roomStatus` 的上报不代表价格没变**
