# 浏览器工作区头部导航与多账号标签方案

> **版本**：v0.3 · 2026-08-06  
> **范围**：OTA 渠道导航、登录账号选择、同 Session 多标签  
> **阶段**：credential 功能链完善中，待手工功能与视觉验收

---

## Context

浏览器工作区同时承载三种不同对象：OTA 渠道、登录账号和网页标签。三者不能继续用相似的横向按钮平铺，否则用户难以判断自己切换的是平台、登录身份还是页面。

本方案进一步明确参考界面中两个 `＋` 的不同职责：

- **标签区 `＋`**：在当前登录账号下新建网页标签，复用当前 Session/partition。
- **账号区 `＋`**：打开当前渠道的已登录账号列表；选择另一个账号后，切换到该账号的 Session/partition。

Electron 中每个 `WebContents` 都必须使用一个 `Session`。`partitionName` 是取得和持久化该 Session 的稳定标识；多个标签使用同一 partition 时，共享 Cookie 等登录数据，但各自拥有独立 URL、标题和导航历史。

因此本设计的核心不是“标签是否需要 partition”——所有 OTA 标签都需要——而是根据用户意图决定：

```text
同一账号新页面  → 复用当前 partition
切换已有账号    → 使用目标 credential 的 partition
登录新账号      → 创建新的 partition
```

## Goals / Non-Goals

**Goals:**

- 用两层头部明确“渠道 → 登录账号 → 页面”的信息层级。
- 明确区分两个 `＋`，避免把“新页面”和“新登录态”混成同一操作。
- 一个渠道同一时刻只打开一个登录账号，但允许该账号打开多个共享 Session 的页面标签。
- 切换账号时关闭原账号页面，但保留其持久化 Session 和 Cookie，以便下次快速恢复。
- 将 Cookie 导入、手动登录、账号刺探、credential 与 partition 的生命周期串成一条可验证链路。
- 在长账号名、多标签和窄窗口下保持当前渠道、当前账号和关键操作可见。

**Non-Goals:**

- 不把酒店或门店作为头部导航层级；门店业务由 OTA 页面内部处理。
- 不允许一个渠道同时显示两个不同登录账号的标签。
- 不自动推断手机号、用户名等当前无法可靠取得的身份。
- 不在本方案中定义删除 credential、删除 partition 磁盘数据或 Cookie 清理策略。
- 不新增标签拖拽、固定标签、恢复关闭标签、跨账号复制页面等浏览器高级能力。
- 不在设计阶段修改代码。

## Decisions

## 1. 产品信息架构

### 1.1 三个层级

```text
渠道 Channel
  └── 当前登录账号 Credential
        └── 页面标签 BrowserTab（一个或多个）
```

| 层级 | 回答的问题 | 生命周期 | 稳定标识 |
|------|------------|----------|----------|
| 渠道 | 我在哪个平台工作？ | 配置级，长期存在 | `channelId` |
| 登录账号 | 当前平台使用哪份登录态？ | 持久化，跨重启存在 | `credentialId` / `partitionName` |
| 页面标签 | 当前账号打开了哪些页面？ | 运行时，关闭即销毁 | `tabId` |

酒店或门店可能是账号探测的业务结果，但不是本头部的信息层级。特别是一个登录 credential 可能关联多家门店，不能把每条门店记录误显示成独立登录会话。

### 1.2 头部整体线框图

```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 渠道行 · 64px · bg #F4F6FA                                                       │
│                                                                                  │
│  [携程] [美团酒店] [美团民宿] [飞猪] [ 抖音来客·当前 ] [小红书] [Booking] …     │

│                                                                                  │
```

模块横向布局：

```text

┌──────────────┬──────────────────────────────────────┬─────────────────────────┐
│ 浏览器控制区  │ 页面标签区                           │ 当前账号区               │

       12px gap                                         12px gap
```

背景与层级：

```text
应用内容画布                    #FFFFFF
  └─ 渠道行                     #F4F6FA
       ├─ 普通渠道              transparent
       ├─ hover                 #EAEDF3
       └─ 当前渠道              #FFFFFF + 1px #E2E6EC + 轻阴影
  └─ 页面工作栏                 #FAFBFC
       ├─ 浏览器控制            transparent；hover #EEF1F5
       ├─ 标签槽                #F0F2F5；圆角 12px
       ├─ 非当前标签            transparent；hover #E8EBEF
       ├─ 当前标签              #FFFFFF + 1px #E2E6EC
       ├─ 当前账号              #FFFFFF + 1px #5645D4
       └─ 两个 ＋               transparent / white，按所属模块区分
```

头部由当前三行约 150px 收敛为两行 128px。参考图原始截图为 `1672 × 148px`，两行约为 68px 与 70px；本方案保留其浏览器式比例，但统一收敛为两个 64px 行高，便于组件对齐和窗口缩放。

- 第一层只切换渠道。
- 第二层左侧是浏览器控制，中间是当前账号的页面标签，右侧是当前登录账号。
- 页面标签和账号控件视觉上分区，不能让两个 `＋` 紧挨或使用相同 Tooltip。
- 两行背景使用相邻但不同的浅色：渠道行稍深，页面工作栏稍浅；当前渠道、当前标签和当前账号使用白色表面形成三处清晰锚点。
- 所有可点击控件沿各自行的垂直中线对齐，不使用顶部或底部参差对齐；标签不贴住内容区底边，保持参考图中的独立圆角卡片形态。

### 1.3 两个 `＋` 的职责对照

| 控件 | 位置 | Accessible name / Tooltip | 用户意图 | partition 策略 |
|------|------|---------------------------|----------|----------------|
| 标签 `＋` | 页面标签末尾 | `新建标签页` | 当前账号再开一个页面 | 复用当前 partition |
| 账号 `＋` | 当前账号右侧 | `切换登录账号` | 查看当前渠道已登录账号 | 列表选择后使用目标 partition |
| 从 Cookie 导入 | 账号列表右上角 | `从 Cookie 导入` | 导入后直接打开当前渠道 | 创建新 partition 并注入当前渠道 Cookie |
| 登录新账号 | 账号列表右上角 | `登录新渠道账号` | 建立一份新登录态 | 创建新 partition |

账号区 `＋` 虽然采用加号图形，但行为不是立即创建 partition，而是先进入账号选择列表；真正创建新 partition 的入口在列表内部，分别是“从 Cookie 导入”和“登录新渠道账号”。

Cookie 导入保留两个入口及不同收尾流程：

```text
初始化提示导入  → 导入 Cookie → 设置页 → 已导入 Cookie 列表 → 用户选择渠道登录
账号列表内导入  → 导入 Cookie → 直接取当前渠道 → 创建登录 partition → 打开工作区
```

两个入口复用同一个浏览器来源选择组件和现有 `cookies.import` 能力。账号列表入口不导航设置页，也不展示已导入 Cookie 列表；若当前渠道没有可用 Cookie，则沿用 `createFromCookie` 的明确失败并保留原账号页面。

## 2. Session、partition、credential 与标签的关系

### 2.1 核心关系

```text
OtaCredential
  ├── credentialId
  ├── channelId
  └── partitionName ───────────────┐
                                   ▼
                        Electron Session
                        ├── Cookies
                        ├── HTTP Cache
                        ├── LocalStorage / IndexedDB
                        └── Service Worker 等
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
                BrowserTab A   BrowserTab B   BrowserTab C
                WebContents     WebContents     WebContents
                URL 独立        URL 独立        URL 独立
                历史独立        历史独立        历史独立
```

约束：

1. 一个持久化 partition 对应一份 Electron Session。
2. 一个 credential 持有一个权威 `partitionName`。
3. 一个 credential 可以同时对应多个 BrowserTab。
4. 同一 credential 的所有 BrowserTab 必须使用同一 Session。
5. 页面关闭只销毁 WebContents，不删除 credential、partition 或 Cookie。
6. Session 必须在创建 WebContents 时指定，页面开始导航后不再切换 partition。
7. 新 partition 探测到同渠道同 `channelAccountId` 时复用原 credential ID，并把其权威 `partitionName` 更新为新值。
8. 被替换 partition 先标记退休；仍有 BrowserTab 引用时延迟处理，最后一个引用关闭后通过 Electron Session API 清空存储与缓存，不直接操作 Chromium 磁盘目录。

### 2.2 持久化与命名

新登录态的 partition 使用持久化前缀，概念格式为：

```text
persist:<app>:<environment>:<channel>:<random-id>
```

例如：

```text
persist:xiaozhi:prod:ctrip:a1b2c3d4
persist:xiaozhi:prod:douyin:e5f6g7h8
```

命名原则：

- 在“开始登录”时生成，而不是刺探成功后生成。
- 尾部使用随机短 ID，避免同渠道不同账号写入同一 Cookie 容器。
- 不使用手机号、酒店 ID 或账号 ID 推导，因为创建 partition 时这些身份可能尚未知。
- 创建后原样保存到 credential；以后打开账号只读取，不重新计算。
- `persist:` 表示登录数据落盘，应用重启后仍可复用。

### 2.3 Cookie 的四种来源

| 操作 | partition | Cookie 来源 | 是否刺探 |
|------|-----------|-------------|----------|
| 标签区 `＋` 新页面 | 当前 credential 的已有 partition | partition 中已经保存的 Cookie | 否 |
| 选择已有账号 | 目标 credential 的已有 partition | 目标 partition 中已经保存的 Cookie | 否 |
| Cookie 列表“登录账号” | 新建 partition | 把导入暂存区的 Cookie 注入新 Session | 是 |
| “登录新渠道账号”手动登录 | 新建 partition | 用户登录后由 OTA 网站写入 Session | 是 |

复用已有 partition 时不应再次从 Cookie 导入文件复制 Cookie。Session 自己就是登录态事实来源，重复注入会覆盖用户在之后登录过程中刷新的 Cookie。

## 3. 标签区 `＋`：同一 Session 新建页面

### 3.1 前置条件

标签区 `＋` 只有在以下条件成立时可用：

- 已选择当前渠道；
- 当前渠道存在活动标签；
- 活动标签能解析出当前 credential/partition。

若当前渠道没有登录账号，标签 `＋` 不创建空白或默认 Session 页面；应禁用并通过 Tooltip 提示“请先选择登录账号”。账号选择由右侧账号 `＋` 承担。

### 3.2 操作流程

```text
用户点击标签区 ＋
        │
        ▼
读取当前 activeTab
        │
        ├─ 无 activeTab / 无 partition ──► 不创建；提示先选择登录账号
        │
        ▼
取得 activeTab.partitionName
        │
        ▼
取得同一 Electron Session
        │
        ▼
创建新的 WebContents / BrowserTab
        │
        ▼
加载当前渠道默认入口 URL
        │
        ▼
激活新标签；原标签保留
```

新标签行为：

- 默认加载当前渠道首页，不复制原标签的当前 URL。
- 继承当前 credential 的登录态。
- 不新建 pending partition。
- 不创建或更新 credential。
- 不挂账号刺探回调。
- 新标签的后退、前进、刷新、标题和加载状态独立。

选择“渠道默认入口”而不是复制当前 URL，是因为 `＋` 表达新工作页；复制详情页可能重复提交带临时参数的业务页面。后续若需要“复制标签页”，应作为独立操作设计。

### 3.3 共享 Session 的联动边界

```text
标签 A 登出账号
       └── 修改共享 Session Cookie
                 └── 标签 B / C 后续请求同样失去登录态

标签 B 登录成另一个账号
       └── 覆盖共享 Session Cookie
                 └── 标签 A / C 实际身份同时变化
```

这是复用 Session 的预期结果，不是标签隔离缺陷。产品上一个 credential 下的标签必须始终被视为同一登录身份；若用户要登录另一个账号，应使用账号列表中的“登录新渠道账号”，不能在普通新标签中切换身份。

## 4. 账号区 `＋`：已登录账号列表

### 4.1 列表线框图

```text
┌──────────────────────────────────────────────────────────────────────┐
│ [渠道图标] 已登录账号列表                   [登录新渠道账号]   [×] │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│ ┌──────────────────────────────────────────────────────────────────┐ │
│ │ [✓ 已打开]  携程                                                │ │
│ │ 当前使用账号：银际酒店账号                          [删除]      │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│ ┌──────────────────────────────────────────────────────────────────┐ │
│ │ [未打开]    携程                                                │ │
│ │ 账号：璞禾酒店账号                                  [删除]      │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

列表规则：

- 只展示当前渠道的 credential，不把其他渠道混入列表。
- 数据源直接读取当前渠道的 `OtaCredential`；不从 `OtaAccount` 反推 credential。
- 同一非空 `channelAccountId` 的多条 credential 在账号列表合并为一项；默认使用最近发现的 credential，当前活动 partition 属于该身份时优先保留当前 credential。
- 没有稳定 `channelAccountId` 的 credential 按 partition 独立展示；credential 没有关联门店时也必须展示。
- 当前渠道任意标签使用该 partition 时，状态为“已打开”。
- 其他 credential 状态为“未打开”。
- 主标签优先使用 `credentialExtra` 中经过白名单保存的渠道账号名称，其次使用 `channelAccountId`，最终回退“未识别账号”。
- 本工作区不读取或展示 `OtaAccount` 门店信息；门店是 credential 关联的业务数据，不是登录态选择项。
- “删除”涉及 credential 和磁盘 Session 生命周期，保持为独立后续方案；本设计只保留位置参考，不定义其执行行为。

### 4.2 打开列表

`WebContentsView` 是原生合成视图，可能盖住 renderer HTML 面板。因此打开账号列表前，需要临时隐藏当前 BrowserTab 的原生视图；关闭列表且未切换账号时，再恢复原活动标签。

```text
点击账号区 ＋
      │
      ▼
记录当前 activeTabId
      │
      ▼
隐藏当前 WebContentsView
      │
      ▼
查询当前渠道 credential 列表
      │
      ├─ 成功 ─► 展示账号列表
      └─ 失败 ─► 展示错误；关闭后恢复原 activeTab
```

### 4.3 选择另一个账号

产品结果是：关闭原账号标签，使用目标账号打开一个新的默认标签。

实现顺序采用“先打开目标、成功后关闭原标签”，避免目标 Session 打开失败后工作区变空：

```text
用户选择目标 credential
          │
          ▼
校验 credential.channel == 当前 channel
          │
          ▼
读取目标 credential.partitionName
          │
          ▼
用目标 Session 创建默认页面标签
          │
          ├─ 创建失败
          │     ├─ 关闭账号列表
          │     ├─ 恢复原 activeTab
          │     └─ 保留原账号全部标签
          │
          ▼ 创建成功
激活目标账号新标签
          │
          ▼
关闭当前渠道中属于原 credential 的全部旧标签
          │
          ▼
账号列表关闭；头部显示目标账号
```

最终不变量：

```text
对任一 channel：所有已打开 BrowserTab 的 partitionName 必须相同
```

切换账号关闭旧标签，但不执行以下操作：

- 不清理旧 partition Cookie；
- 不删除旧 credential；
- 不删除账号探测结果；
- 不创建新的目标 credential；
- 不再次触发刺探。

以后重新选择旧账号时，使用其原 partition 打开新标签，登录态仍可恢复。

### 4.4 点击当前已打开账号

若用户点击带“已打开”状态的当前账号：

- 不关闭或重建标签；
- 关闭账号列表；
- 恢复此前活动标签。

这避免无意义刷新和用户页面上下文丢失。

## 5. 登录新渠道账号

### 5.1 手动登录流程

账号列表右上角“登录新渠道账号”用于建立新的登录身份：

```text
点击“登录新渠道账号”
          │
          ▼
为当前 channel 生成新 partitionName
          │
          ▼
创建持久化 Session（初始无业务 Cookie）
          │
          ▼
记录 pending partition
          │
          ▼
打开渠道登录页并等待用户登录
          │
          ▼
URL / 页面事件命中登录成功条件
          │
          ▼
触发账号与 credential 刺探
          │
          ├─ 刺探失败 ─► 保留 pending，标签继续可用/允许重试
          │
          ▼
创建或更新 OtaCredential
  credential.partitionName = 新 partitionName
          │
          ▼
绑定发现的账号/门店，移除 pending
```

登录页面本身就是新 credential 的第一个标签。刺探完成前，头部账号文案显示“正在登录”或“未识别账号”；完成后更新为可识别账号标签。

### 5.2 Cookie 导入后登录

设置页“已登录 Cookie 列表 → 登录账号”走另一条创建入口，但 partition 原则相同：新建而不是复用其他 credential。

```text
浏览器 Cookie 导入
      │
      ▼
按渠道暂存导入 Cookie
      │
      ▼
设置页点击“登录账号”
      │
      ▼
为该渠道生成新 partitionName
      │
      ▼
创建持久化 Session
      │
      ▼
把暂存 Cookie 注入该 Session
      │
      ▼
打开新的浏览器标签并跳转工作区
      │
      ▼
触发渠道账号/credential 刺探
      │
      ▼
credential 绑定 partitionName；pending 被消费
```

为什么 Cookie 导入仍然创建新 partition：

- 导入文件只说明“某渠道有一份候选登录态”，不能安全判断它属于哪个已有 credential。
- 注入已有 partition 可能覆盖用户当前有效 Cookie。
- 新 partition 让刺探结果和登录态从一开始一一对应；识别成功后再由 credential 持久化关联。

## 6. 渠道与账号切换状态模型

### 6.1 每个渠道独立保存工作状态

```text
WorkspaceState
  ├── activeChannelId
  └── channelStates[channelId]
        ├── activeCredentialPartitionName
        ├── activeTabId
        └── tabs[]                 # 全部使用同一 partition
```

渠道切换与账号切换不同：

| 操作 | 是否关闭当前标签 | 是否改变 partition | 是否新建 Session |
|------|------------------|--------------------|------------------|
| 切换渠道 | 否，隐藏并保留原渠道状态 | 切到目标渠道自己的当前 partition | 否 |
| 标签区 `＋` | 否 | 否 | 否 |
| 切换已有账号 | 是，关闭原账号标签 | 是，使用目标 credential partition | 否 |
| 登录新账号 | 最终切到新账号 | 是，新 partition | 是 |

渠道 A 与渠道 B 可以各自保留一个已打开 credential；“一个渠道只打开一个登录账号”的约束只在渠道内部生效。

### 6.2 状态不变量

实现和测试必须守住以下不变量：

```text
I1. 每个 BrowserTab 都有非空 partitionName
I2. 同一渠道当前打开的所有 BrowserTab 共享同一 partitionName
I3. 标签区 ＋ 不创建 partition
I4. 切换已有账号不复制或注入 Cookie
I5. 登录新账号和 Cookie 登录始终创建新 partition
I6. 关闭账号标签不删除 Session 或 credential
I7. 当前账号由 activeTab.partitionName 派生，不维护可漂移的第二份选择状态
```

- 当前标签：白色表面、完整圆角和细描边；不贴住内容区底边，保持参考图中的悬浮标签形态。
- 非当前标签：透明背景、`#5F6673` 文字；相邻标签之间可使用 1px `#E7E9ED` 短分隔线，悬停后改为完整弱背景。
- 关闭按钮：常态低对比度，悬停或键盘聚焦时增强。
- 加载中：标签内展示小 spinner；刷新按钮同步表达加载状态。
- 登录待识别：账号区显示“正在登录”，不伪造账号名。
- 所有标签、浏览器按钮、当前账号和两个 `＋` 均沿页面工作栏的 32px 中线对齐，图标不得因文字高度产生上下偏移。

### 7.4 工作区网页声音开关

声音开关采用单一运行期状态，不跟随渠道、credential 或 partition 分组：

```text
BrowserManager.audioMuted
  ├── 状态变化 → 对当前全部 ManagedTab 调用 webContents.setAudioMuted
  └── 创建标签 → 新 WebContents 在加载 URL 前读取并应用同一状态
```

- 默认允许网页声音；点击后在“允许声音 / 全部静音”之间切换。
- renderer 只通过受控 IPC 读取和设置该布尔状态，不取得 WebContents ID。
- 新页面、新账号和切换账号产生的标签走同一个 `createTab` 入口，因此统一继承。
- 本期不跨应用重启持久化，不注入 OTA DOM，也不实现 OTA 页面自身缺失的业务播报。

## 8. 失败与边界处理

| 场景 | 处理 |
|------|------|
| 无当前账号时点击标签 `＋` | 不创建默认 Session 标签；提示先选择账号 |
| 目标 credential 不属于当前渠道 | 拒绝切换并记录上下文错误 |
| 目标 partition 已丢失磁盘 Cookie | 页面可能落到登录页；标记登录失效，不回退共享 Session |
| 切换账号时目标标签创建失败 | 保留并恢复原账号全部标签 |
| 账号列表加载失败 | 保持原 activeTab，可关闭面板后恢复 |
| 当前账号有未提交表单 | 切换会关闭标签并丢失页面态；账号切换前需要二次确认策略时另立需求，本期按直接切换 |
| 同一 Session 某标签主动退出 | 其他标签共享 Cookie，后续同步失效；统一显示该 credential 登录失效 |
| 刺探未支持当前渠道 | 新 partition 和登录标签可存在，但保持未识别状态，不伪造 credential |
| 同 credential 关联多家门店 | 账号列表仍只显示一项，可辅助显示关联门店数量 |

## 9. 方案取舍

### 9.1 为什么不是每个标签一个 partition

每个标签创建独立 partition 会导致同一账号重复登录、Cookie 无法自然同步、磁盘 Session 数量失控，也让“账号”与“页面”失去明确关系。因此否决。

### 9.2 为什么普通新标签不创建新 credential

标签表达页面工作上下文，不表达新身份。只有用户明确选择“登录新渠道账号”时，系统才创建新登录态。否则一个普通 `＋` 就可能悄悄产生无法识别的 pending credential。因此否决。

### 9.3 为什么切换账号关闭旧标签

保留不同 credential 的标签并混排，会让标签标题无法表达其登录身份，用户也可能在错误账号中操作。每个渠道仅保持一个打开 credential，可以使右侧“当前登录账号”对整组标签都成立。

代价是切换账号会丢失旧标签的页面位置；但其 Session/Cookie 不删除，下次切回无需重新登录。后续若确有跨账号并行工作需求，应升级为账号分组标签，而不是破坏当前单账号不变量。

### 9.4 为什么切换时先创建目标标签再关闭旧标签

用户看到的最终结果仍然是旧标签关闭、新账号打开；内部先创建目标标签是为了失败回滚。如果先关闭旧标签再发现目标 partition 无法打开，工作区会直接变空。

### 9.5 为什么账号列表使用覆盖层而不是常驻第三行

账号切换是低于渠道、页面的阶段性操作，适合渐进披露。常驻第三行既占空间，又会把 credential 与页面标签呈现成相同层级。因此使用覆盖层。

## Risks / Trade-offs

- [共享 Session 使一个标签的登录/登出影响其他标签] → 将同 partition 标签明确视为一个账号工作组；切换身份必须走账号入口。
- [部分渠道 credential 身份仍是临时或不可读标识] → 优先使用 credential 白名单身份字段；无法确认时使用中性回退文案，不读取门店账号补名。
- [切换账号会丢失旧标签页面位置] → 保留持久化 Session，重新选择时免登录；跨账号标签恢复另立需求。
- [账号面板可能被原生 WebContentsView 遮挡] → 打开前 hide，关闭或失败时恢复原 activeTab。
- [切换目标页面创建成功、关闭旧标签中途失败] → 关闭操作按目标 partition 过滤并允许幂等重试，当前账号始终由 activeTab 派生。
- [导入 Cookie 重复使用会先生成新的候选 partition] → 不在注入前猜测身份；刺探得到稳定 `channelAccountId` 后复用原 credential、切换到新 partition，并在旧 partition 无标签引用后清空其 Session 数据。
- [旧 partition 清理失败] → 不回滚已经成功的 credential 身份绑定；保留退休状态供当前进程后续关闭标签时重试，并记录不含凭据内容的告警。
- [参考界面的删除按钮涉及破坏性生命周期] → 本方案不实现删除；另行设计可恢复性、引用检查和磁盘清理。
