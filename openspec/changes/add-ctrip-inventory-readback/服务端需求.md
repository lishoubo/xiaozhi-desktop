# 服务端需求：携程房量回读上报（inventoryReadback）

> 面向 rms-server。desktop 侧实现见 `openspec/changes/add-ctrip-inventory-readback/`。
>
> **服务端工作量预估：新增一个 `AppChangeTranslator` 的 `@Component`，不改任何现有代码。**

## 1. 背景：这条上报解决什么

现有 `POST /api/v1/app/ota-changes` 报的是「**用户想改成什么**」—— 渠道的写请求原始报文。

但携程房量的「增加 / 减少」是**相对操作**：批量页的 `remainRoomQuantityType: 11`(加) / `12`(减) 只说「+2」，不说基数。RMS 收到后**算不出改后的绝对房量**。

而且携程的写接口**不回传改后状态**：
- 日历页响应 `{"code":200, "message":"房量设置成功。", "data":null}`
- 批量页响应 `{"taskId":"...", "resStatus":{"rcode":200}}` —— 且这是**异步任务**，受理成功不代表已写库

所以 desktop 在用户改动成功后，主动**回读**一次渠道的真实状态，把结果作为**第二条上报**发来。

```
用户在携程改房量
    │
    ├─→ 上报 A（既有）：changeType=roomStatus  「用户想改成什么」
    │
    └─→ 上报 B（本需求）：changeType=inventoryReadback  「实际变成了什么」
```

## 2. 接入方式

**复用现有端点 `POST /api/v1/app/ota-changes`，报文结构不变。**

服务端的 `AppChangeTranslatorRegistry` 按 `(source, endpointId)` 分派，Translator 由 Spring 注入 `List<AppChangeTranslator>` —— 新增一个 `@Component` 即可，注册表本身不用改。

分派键：

| 字段 | 值 |
|---|---|
| `source` | `CTRIP` |
| `endpointId` | `getRoomInventoryInfo` |
| `changeType` | `inventoryReadback`（**新值**，服务端只进日志，不参与分派） |

> `endpointId` 用的是**回读接口**的名字，不是触发它的写端点 —— 后者（`setbatchroombookablestatus` / `batchUpdateRoomStatusAndQuantity`）已被既有 Translator 认领，复用会撞键。

⚠️ **先决条件：`change_type` 列必须先扩到 `VARCHAR(32)`**，否则本链路整条 500、数据一条都不落库 —— 根因见文末。DDL 执行后，未认领的 `endpointId` 才会按既有约定落 `raw_body` + `UNKNOWN_ENDPOINT`。

顶层字段与既有上报完全一致，差异全在 `changeRaw`：

```json
  "otaHotelId": "122244992",
  "channelAccountId": "...",
  "channelAccountName": "...",
  "submitAt": "2026-09-18T10:00:03.000Z",
  "changeRaw": {
    "trigger": {
      "endpointId": "batchUpdateRoomStatusAndQuantity",
      "observedAt": "2026-09-18T10:00:00.000Z",
      "rawRequest": {
        "roomProductIds": ["1569052069"],
        "dates": {
          "dateRanges": [{ "startDate": "2026-10-20", "endDate": "2026-10-20" }],
          "weekDays": ["SUNDAY","MONDAY","TUESDAY","WEDNESDAY","THURSDAY","FRIDAY","SATURDAY"],
          "applyAllDates": false
        },

        "roomQuantityLimitType": 1,
        "remainRoomQuantityType": 11,

      }
    },

      {
        "hotelID": 122247738,
        "roomTypeID": 1569052069,

```

### 3.1 `changeRaw.trigger` —— 这次回读是谁触发的

| 字段 | 含义 |
|---|---|
| `endpointId` | 触发本次回读的**写端点**，取值 `setbatchroombookablestatus`（日历页）或 `batchUpdateRoomStatusAndQuantity`（批量页） |
| `observedAt` | 写请求被拦到的时刻 |
| `rawRequest` | 写请求原始报文，已剔除框架噪音字段（`reqHead` / `cipher` / `head` / `holidyInfo`），其余原样 |

`rawRequest` 的字段语义已在既有规格文件里写明，**不重复**：
- 日历页 → `apps/desktop/src/main/channels/ctrip/room-status-payload.ts`
- 批量页 → `apps/desktop/src/main/channels/ctrip/room-status-quantity-payload.ts`

### 3.2 `changeRaw.cells` —— 回读到的事实

携程 `getRoomInventoryInfo` 返回行的**原样透传**，desktop 不做任何映射或类型转换。一行 = 一个房型 × 一天。

| 字段 | 类型 | 含义 |
|---|---|---|
| `hotelID` | number | ⛔ **不可用于匹配门店**，见 §4.3 |
| `roomTypeID` | number | 售卖房型 ID |
| `effectDate` | string | `YYYY-MM-DD` |
| `payType` | string | `PP` 预付 / `FG` 现付 |
| `roomStatus` | string | `"G"` 有保量开放 / `"N"` 系统关房 / `"Y"` 手动关房 |
| `limitSale` | string | `"T"` 限量 / `"F"` 不限量 |
| `freeSale` | string | `"T"` FreeSale |
| `totalQuantity` | number\|null | 总房量 |
| `canUsedQuantity` | number\|null | 可用房量 |
| `hasInventory` | boolean | ⚠️ 见 §4.1 |

⚠️ `roomStatus` 是**字符串** `"G"/"N"/"Y"`。注意与批量页写报文的 `roomStatus`（数字 `1`/`2`/`-100`）**不是一回事**，两者在同一份报文里同时出现。

## 4. 五条反直觉约定（务必读）

### 4.1 `limitSale: "F"` 时房量 0 **不代表没房**

不限量 / FreeSale 时房量字段本来就是 0，`hasInventory` 也可能是 `false`，但**实际有房**。

人工标注的真实样本（来自 `docs/踩点/携程/日历页面-房量.md`）：

| 页面显示 | limitSale | freeSale | totalQuantity | canUsedQuantity | 说明 |
|---|---|---|---|---|---|
| 限量 剩7 | `"T"` | — | 9 | 7 | 正常限量 |
| FS | `"F"` | `"T"` | 0 | 0 | `hasInventory:false` 但**有房** |
| FS 剩1 | `"F"` | — | 1 | — | `roomStatus:"N"` |
| 不限 | `"F"` | — | 0 | — | `hasInventory:false` 但**有房** |

**判读顺序**：先看 `freeSale === "T"` → 不限量；否则看 `limitSale`，`"T"` 才读房量数字。

⛔ **不要仅凭 `totalQuantity` / `hasInventory` 判定无房** —— 会把不限量的房型判成满房。

### 4.2 `applyAllDates: true` 时，这份数据**不是完整快照**

用户勾选「应用到所有日期」时，携程侧会修改**从今日起约两年**的日期，并且会改变**未显式设置过的日期的默认值**（是否限量、房态等）。

这个影响范围 desktop **算不出来**（要知道哪些日期被设置过，本身就得先有全量快照），也不可能回读两年。

**desktop 的处置**：只回读未来 7 天（可配置），`cells` 里只有这 7 天。

**服务端须据此判断**：`changeRaw.trigger.rawRequest.dates.applyAllDates === true` 时，**不可**认为「`cells` 里没出现的日期就是没变」—— 第 8 天及以后的状态未知。

### 4.3 `cells[].hotelID` **不可用于匹配门店**

携程有三个「酒店 id」，混用不报错、只会静默错价或集体不跟价：

| id | 典型值 | 用途 |
|---|---|---|
| `ota_account.ota_hotel_id` | `122244992` | **账号粒度，唯一身份依据** |
| 报文顶层 `otaHotelId` | `122244992` | 与上一行**同源同值** |
| `cells[].hotelID` | `124241180` / `122247738` | 携程内部「**门店 × 售卖模式**」层（同店 PP/FG 各一个） |

**匹配门店请用顶层 `otaHotelId`**（desktop 已用凭证的 `masterHotelId` 归一过，与绑定探测口径一致）。`cells[].hotelID` 仅作存档。

⚠️ 后果具体：`ota_hotel_id` 是 `uk_ota_sale` 第 4 列，值不对 → upsert 撞不上唯一键 → INSERT 新行 → 同一房型两行。

### 4.4 `cells` 的日期范围**已经是精确范围**，无需再按星期过滤

desktop 侧已经把日期区间与星期筛选取过交集，`cells` 里的日期**恰好**是用户本次改动实际影响的那些天。

```
用户操作：8/31~9/6 区间，只勾周六周日
rawRequest：dateRanges 给 7 天区间 + weekDays 给 ["SATURDAY","SUNDAY"]
cells：     只有 9/5、9/6 两天                    ← 已过滤好
```

⚠️ **服务端不要再拿 `rawRequest` 里的日期区间去展开** —— 那是 7 天，会比实际多跟 5 天。要跟价直接用 `cells[].effectDate`。

desktop 侧的星期解析与服务端 `RawBodyReader.weekdaysFromBitString` / `weekdaysFromNames` **同口径**（位串最左=周一、空数组=不过滤），两边算出的日期集合应当一致。

### 4.5 ⚠️ 回读不区分房态与房量，重复内容**由服务端裁剪**

desktop **不判断**本次改动动的是房态还是房量 —— 回读接口返回的行本来就同时含两者，**整行照报**。

所以同一份房态信息会出现**两次**：

```
上报 A (changeType=roomStatus)       changeRaw.roomStatus = 2        ← 用户想关房
上报 B (changeType=inventoryReadback) cells[].roomStatus = "N"        ← 实际已关房
                                      cells[].totalQuantity = 6       ← 顺带带来的房量
```

**这是刻意的，不是冗余 bug。** desktop 侧不做裁剪的理由：让客户端判断「房态已经报过了所以这次只报房量」会引入一个易错的语义判断，而它的失效方式是**静默丢数据**；多报一份的代价只是冗余。

**服务端按需取用即可**：

- 只关心房量 → 读 `cells[].totalQuantity` / `canUsedQuantity` / `limitSale` / `freeSale`
- 只关心房态 → 读 `cells[].roomStatus`（注意是字符串 `"G"/"N"/"Y"`，与上报 A 的数字码不同）
- 两者都要 → 整行用

⚠️ 上报 A 与上报 B 的房态**取值形式不同**（A 是写报文的 `1`/`2`/`-100` 或 `"G"`/`"N"`，B 是读接口的 `"G"`/`"N"`/`"Y"`），不可混用同一套解析。

⚠️ 若两者冲突（A 说要关房、B 读到仍是开房），**以 B 为准但要警惕**：可能是批量页异步写入尚未生效（见 §6 的任务门控说明），而不是改动失败。

## 5. `operationId` 独立，不可互相去重

一次用户改动会产生**两条**上报，携带**不同的** `operationId`：

| | changeType | 内容 |
|---|---|---|
| 上报 A | `roomStatus` | 用户想改成什么（写请求报文） |
| 上报 B | `inventoryReadback` | 实际变成了什么（回读结果） |

⛔ **两者是两个独立事实，不可互相去重。** 把 B 当成 A 的重复而丢弃，就失去了本需求的全部价值。

## 6. 其他须知

- **只有渠道判定成功的改动才会触发回读** —— 渠道拒绝的改动不会产生上报 B。
- **偶发漏报是已知取舍**：回读失败不重试、不落盘（与既有上报口径一致）。所以「有 A 无 B」是正常情况，**不该按错误告警**。
- ✅ **`cells` 是改后的值**。批量页写接口是**异步**的（`rcode:200` 只代表受理），
  desktop 会拦页面自己对 `queryMainTaskInfoForDisplay` 的轮询、**等到渠道任务
  `status: SUCCESS` 才回读**（`ctrip/batch-task-gate.ts`）。2026-09-18 真机验证房量准确读回。
- ⚠️ **等不到任务完成（30s 超时）时 desktop 不发上报 B** —— 宁缺勿错，不报一份可能是旧值的
  数据。这是「有 A 无 B」的第二种正常成因。
- **desktop 不判断读到的是新值还是旧值** —— 相对改动不知道基数，无法判断。读到什么报什么。
- `cells` 可能为空（成功但无数据），这与失败是**不同**的情况。

## 7. ⚠️ 首次真机验证的实测结果（2026-09-18）

desktop 侧已实现并真机跑通，**服务端当前会 500**。

### 实测链路（日历页，改 3 个房型 1 天的限量设置）

```
16:48:16.031  Amount change observed            endpointId=setbatchroombookablestatus
16:48:16.223  上报 A 成功                        ← 既有链路，200
16:48:16.402  Ctrip inventory readback finished  kind=ok, cellCount=3, durationMs=366
16:48:16.505  上报 B 被拒                        ← rmsCode=10000，重试一次后放弃
```

回读侧数据正确：3 房型 × 1 天 = 3 条 cells，不多不少。

### ⚠️ 与设计预期不符的地方，需要服务端确认

设计时的预期是：**未被任何 Translator 认领的 `endpointId` 会落 `raw_body` 并返回
`200 + status=UNKNOWN_ENDPOINT`**，报文先沉淀、不丢，从而 desktop 可以先上线。

实测拿到的却是 `rmsCode: 10000`（`ErrorCode.INTERNAL_ERROR`，HTTP 500）。

**这两者不一样**：

| | 报文是否落库 | desktop 能否先上线 |
|---|---|---|
| 200 + `UNKNOWN_ENDPOINT` | ✅ 落 `raw_body` | ✅ 数据不丢 |
| 500 `INTERNAL_ERROR` | ❌ **一条都不落** | ❌ 数据全丢 |

### ✅ 根因已定位（详见文末）

`change_type` 列是 `VARCHAR(16)`，而 `"inventoryReadback"` 有 **17 个字符**。

两个原先的猜测**都不对**：DTO 反序列化没问题（`changeType` 是普通 `String`，无枚举校验、
无 `@NotBlank`），Translator 那条路径也没走到（`translate()` 在 insert 之后）。异常发生在
`changeTargetMapper.insert(po)` 这一行，所以**报文一条都没落进 `raw_body`**。

因此「desktop 先上线、服务端后补」这个前提**不成立** —— 必须先执行 DDL。

⚠️ desktop 侧**不重试、不落盘**（失败重试 1 次后放弃，与既有上报同一取舍），所以服务端
500 期间的回读数据是**真的丢了**，不会自动补回来。

## ⛔ 500 的根因已定位：`change_type` 列宽不够（两个渠道同因）

**不是** DTO 反序列化炸了，**也不是** Translator 查找失败 —— 是数据库列宽：

```sql
-- V81__app_ota_change_target_change_type.sql
ALTER TABLE app_ota_change_target
  ADD COLUMN change_type VARCHAR(16) NULL ...
```

`"inventoryReadback"` 是 **17 个字符**，超 1 位。

链路：`AppOtaChangeIngestService.insertReceived()` 无条件
`po.setChangeType(trimToNull(req.getChangeType()))` → mapper 的 insert 含 `change_type`
→ MySQL 严格模式 `Data too long for column 'change_type'` →
`DataIntegrityViolationException`。而 `insertReceived` 的外层**只 catch
`DuplicateKeyException`**，异常一路冒到全局处理器 → `INTERNAL_ERROR(10000)` / HTTP 500。

### ⚠️ 由此推出的两个结论

1. **数据 100% 丢失，不是部分丢** —— 异常发生在 `changeTargetMapper.insert(po)` 这一行，
   行根本没插进去，`raw_body` 一条都没有。
2. **在 DDL 执行前，永远走不到 `UNKNOWN_ENDPOINT`** —— 那条路径在 insert 成功之后。
   所以「Translator 没上线也没关系，报文会先落库」这个预期**不成立**。

### 服务端动作项

```sql
ALTER TABLE app_ota_change_target
  MODIFY COLUMN change_type VARCHAR(32) NULL
  COMMENT 'desktop 声明的改动类型：price / roomStatus / inventoryReadback。仅存档，不参与分支';
```

⚠️ 线上 Flyway 已关闭，需**人工执行**。另：V81 本身在生产是否已执行也需一并核实。
