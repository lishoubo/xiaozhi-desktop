# GlitchTip 部署需求（给后端）

> 桌面客户端「小智酒店管家」目前没有任何远程错误上报，出问题只能让业户手动打包
> 本地日志发回来。这份文档只描述**需要后端部署什么**，客户端侧改动不在此文范围。
> 目标是先部署一套试跑，验证通了再接客户端。

## 一、要部署什么

**GlitchTip** —— 开源的错误追踪服务，兼容 Sentry 协议。

选它的原因：

| 诉求 | 说明 |
|---|---|
| 数据不出自己服务器 | 上报内容会夹带渠道 cookie 和酒店经营数据，不能用 SaaS |
| 兼容 Sentry 协议 | 客户端用官方 `@sentry/electron` SDK，native crash / 离线补传 / 崩溃捕获都是 SDK 白送的，不用自己写 |
| 轻量 | 官方 Sentry 自托管要 20+ 容器，GlitchTip 是其精简实现 |

官方部署文档：https://glitchtip.com/documentation/install

## 二、组件构成

```
                 ┌──────────────────────────────┐
   客户端上报 ──▶ │  Nginx (HTTPS)               │
   (公网/内网)    └──────────┬───────────────────┘
                            │
                 ┌──────────▼───────────────────┐
                 │  GlitchTip Web (Django)      │  ← 收上报 + 管理界面
                 └──────────┬───────────────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │PostgreSQL│  │  Redis   │  │  Worker  │  ← Celery，后台处理
        └──────────┘  └──────────┘  └──────────┘
```

## 三、部署方式（二选一）

### 方案 A：Docker Compose（推荐）

官方只维护这一条路，`docker-compose.yml` 一把起全套，升级改版本号即可。

### 方案 B：不用 Docker

若 ECS 上不便跑 Docker，按以下拆分：

| 组件 | 建议 |
|---|---|
| PostgreSQL | 用阿里云 RDS，省掉备份和调参 |
| Redis | 用阿里云 Redis |
| Django Web + Celery Worker | ECS 上跑，systemd 守护 |
| Nginx | ECS 上反代 + HTTPS |

⚠️ 方案 B 需自行趟官方未覆盖的部署细节，工作量明显大于 A。**如果 ECS 没有禁止 Docker 的硬性规定，建议直接用 A。**

## 四、资源需求

| 项 | 需求 | 说明 |
|---|---|---|
| CPU / 内存 | 2C4G 起 | 试跑阶段够用 |
| 磁盘 | 50G 起 | 主要是 PostgreSQL；量取决于保留期与上报量 |
| 网络 | 客户端能访问 | 见「网络可达性」 |

## 五、网络可达性（重要）

**上报方是装在酒店前台电脑上的桌面客户端，不是服务器。** 所以：

- 走**公网**：需要域名 + HTTPS 证书。客户端只需访问一个上报端点
- 走**内网**：仅当所有业户机器都在内网可达范围内才可行——请后端确认实际情况

酒店前台网络不稳定，SDK 自带离线队列（断网缓存、联网补传），服务端无需为此做特殊处理。

## 六、配置要求

### 必须

| 配置 | 要求 |
|---|---|
| HTTPS | 必须启用。上报内容含敏感业务数据 |
| 关闭开放注册 | GlitchTip 默认允许任何人注册，**必须关掉**（`ENABLE_OPEN_USER_REGISTRATION=False`） |
| 邮件（可选） | 配了才能发告警通知，试跑阶段可不配 |

### 环境隔离

客户端有 **三套环境**（见 `apps/desktop/src/shared/app-environment.ts`）。请在 GlitchTip 里按环境区分，避免测试数据污染线上：

- 建 **1 个 Organization**，下面建 **1 个 Project**（如 `xiaozhi-desktop`）
- 环境区分由客户端上报时带 `environment` 标签实现，**服务端无需建多个 Project**

## 七、交付物

部署完成后请提供：

| 项 | 说明 |
|---|---|
| **DSN** | 形如 `https://<key>@<你的域名>/<project-id>`，客户端配置要用，**这是唯一必须给到的东西** |
| 管理后台地址 + 账号 | 用于查看上报的错误 |
| 数据保留期设置 | 默认 90 天，如有调整请说明 |

## 八、验收标准

部署完成后，用官方示例验证一次上报链路通畅即可（GlitchTip 界面上有「发送测试事件」的引导）。客户端接入后另行联调。

## 九、暂不需要考虑

- **上报量评估**：试跑阶段量很小，稳定后再按实际调整
- **告警规则**：先跑通链路，规则后续再配
- **数据长期归档**：GlitchTip 会采样、按配额丢弃、默认存 90 天。若后续需要「一条不漏、可用于对账补报」的记录，那是 RMS 侧另建台账的事，与本次部署无关
