# 服务端需求：房量上报条件收窄（inventoryDiff 触发条件变更）

> 面向 rms-server。desktop 侧实现见本目录 `design.md`。
>
> **服务端工作量预估：0 —— 报文结构、字段、分派键全部不变，只是发得少了。**
> 本文的价值在于说清**为什么某些变化不再上报**，以及两个渠道的房量口径，
> 避免服务端按旧频率做容量假设、或把「不再收到」误判成 desktop 故障。

## 1. 这次改了什么

**只改触发条件，不改报文。**

| | 变更前 | 变更后 |
|---|---|---|
| 房态变化 | 上报 | **上报（不变）** |
| 价格变化 | 上报 | **上报（不变）** |
| 房量变化 | 任一字段变了就报 | **仅「总房量变化」或「可售从非 0 变为 0」** |
| 报文结构 | — | **不变** |
| `changeType` / `endpointId` | — | **不变** |

### 为什么收窄

酒店**有订单时房量本来就会变** —— 卖出一间，已售 +1、剩余 −1。旧判据把这类正常销售
全部当成「渠道侧发生了我们不知道的变更」报上来，真机观察到房量上报过于频繁，绝大多数
是销售噪音，不是需要跟进的渠道事实。

```
旧：卖出一间 → 字段变了 → 上报   ← 噪音
新：卖出一间 → 配额没变、也没售罄 → 不报
    改配额   → 总房量变了       → 上报
    最后一间售出 → 可售 0→非0 跃迁 → 上报
```

## 2. 上报触发条件（完整判据）

```
一格发生变化
   │
   ├─ 价格格子 ─────────────────→ 上报
   │
   └─ 房态房量格子
         ├─ 房态字段变了 ───────────────→ 上报
         ├─ 限量 ⇄ 不限量 切换 ─────────→ 上报
         └─ 限量下看房量：
               ├─ 总房量与上次不同 ──────────→ 上报
               ├─ 可售房量「非 0 → 0」跃迁 ──→ 上报
               └─ 其余（纯卖房）────────────→ 不报
```

⚠️ **不限量的格子不参与后两条房量判据** —— 两个渠道在不限量模式下的房量数字都没有
意义（携程恒为 0 但实际有房，美团是哨兵值）。

⚠️ **「可售为 0」只报跃迁那一轮**。售罄是持续状态，每轮都报会让同一格反复刷屏。
已经为 0 且保持为 0 的格子不再重复上报；若恢复有房后再次售罄，会再报一次。

⚠️ **首次见到的格子仍然只建基线、不上报**（既有行为，本次不变）。

## 3. ⚠️ 房量口径：两个渠道完全不同

### 3.1 携程

| 概念 | 取法 |
|---|---|
| 是否不限量 | `freeSale === "T"` 或 `limitSale !== "T"` |
| 总房量 | 限量时取 `totalQuantity`；**不限量时无意义** |
| 可售为 0 | 限量时 `canUsedQuantity === 0`；**不限量时恒为否** |

**⚠️ 不限量时房量数字全是 0，但实际有房**（既有文档已记载的「四条反直觉约定」之一）：

| 页面显示 | limitSale | freeSale | totalQuantity | 实际 |
|---|---|---|---|---|
| 限量 剩 7 | `"T"` | — | 9 | 正常限量 |
| FS | `"F"` | `"T"` | 0 | **有房** |
| 不限 | `"F"` | — | 0 | **有房** |

**判读顺序**（不可颠倒）：

```
freeSale === "T"        → 不限量，soldOut = false、total = null
否则 limitSale !== "T"  → 不限量，同上
否则（limitSale === "T"）→ 限量，才读 totalQuantity / canUsedQuantity
```

⛔ **`hasInventory` 不能用来判售罄**。desktop 本次实测（本地快照库 755 行携程数据）：

```
limitSale = "T"（限量）的 291 行  →  hasInventory 全部为 true，一个 false 都没有
hasInventory = false 的 203 行    →  全部落在 limitSale = "F"（不限量）
```

它更像是「是不是不限量模式」的副产品，不是「还有没有房」 —— 在限量场景下恒为 `true`，
拿它判售罄会得到一条永不触发的判据。限量时可售房量就是 `canUsedQuantity`
（实测限量行里它 0~18 都有，其中 3 行为 0，`roomStatus:"N"`）。

### 3.2 美团

| 概念 | 取法 |
|---|---|
| 是否限量 | `limitType === 1`（`2` = 不限量） |
| 总房量（**配额**） | `limitRemain + usedCount` |
| 可售为 0 | `limitType === 1 && limitRemain === 0` |

**总房量 = `limitRemain + usedCount`**，desktop 本次实测（本地快照库 201 行美团数据）：

| 房型 | `limitRemain + usedCount` |
|---|---|
| 云憩大床房（15 个日期，usedCount 0→5） | **恒为 20** |
| 轻奢标准间（usedCount 1→5） | **恒为 8** |
| 奢华雅致双床房（usedCount 4→10） | **恒为 10** |

**卖出一间时 `limitRemain` −1、`usedCount` +1，和不变** —— 这正是「有订单不误报」
所依赖的不变量。

### ⛔ `remainCount` 是**预留房量**，不要拿它算任何东西

它既不是「剩余可卖」，也不参与总量计算。实测值大多为 0、偶尔 1，与 `limitRemain`
和 `usedCount` **没有算术关系**：

| 房型 | date | `remainCount` | `limitRemain` | `usedCount` |
|---|---|---|---|---|
| 云舒双床房 | 09-25 | 1 | 39 | 1 |
| 云憩大床房 | 09-21 | 0 | 15 | 5 |

⛔ **早期文档里「`remainCount + usedCount` = 物理房量」的说法不成立** —— 云舒双床房
照此算出 2，而该房型配额有 40。若服务端此前按这个公式推算过物理房量，**结果是错的**。

⛔ 更不能拿 `remainCount === 0` 判售罄：实测为 0 的 32 行配额都还有剩，
真正售罄（`limitRemain = 0`）只有 1 行。

**⚠️ 不限量时 `limitRemain` 是哨兵值，不是真实房量**：既有文档记的是 998/999，
desktop 本次在本地库实测到 **1002**（`limitType=2` 的 15 行全部为此值）。
说明**哨兵不是固定的几个数**，判定必须先看 `limitType`，不要做 `limitRemain !== 999`
这类值比较。

## 4. 本次实测到的未文档化取值

以下取值在既有文档里没有记载，desktop 在本地快照库中观察到，供服务端解析时参考：

| 字段 | 未文档化取值 | 出现场景 | 影响 |
|---|---|---|---|
| 美团 `limitRemain` | `1002` | `limitType=2`，15/15 行 | 哨兵值家族不止 998/999 |
| 美团 `roomStatus` | `100` | `usedCount=10, limitRemain=0`（真卖光） | **既有文档只记了 0/1** |
| 美团 `fullRoomCode` | `4`（`fullRoomDesc`:「请补充房型库存」） | 同上那一行 | 既有样本只见过 `3` |

⚠️ **`roomStatus=100` 值得注意**：既有文档的推论是「`0` = 关房或售罄、`1` = 有房」，
服务端若按 `0/1` 二值分派会漏掉这个第三态。desktop 侧不受影响（房态判据是「有改变就报」，
不解读取值），但服务端若要据 `roomStatus` 判断房态语义，需要把它纳入。

## 5. 对服务端的实际影响

| 影响面 | 说明 |
|---|---|
| 报文解析 | **无需改动**，字段与结构完全不变 |
| 上报量 | **显著下降** —— 房量类上报只剩配额变更与售罄跃迁 |
| 容量假设 | 若有基于旧频率的告警阈值/容量规划，需要下调 |
| 「不再收到」的判读 | ⚠️ 有订单的房型不再每轮上报是**预期行为**，不是 desktop 故障 |
| 房量绝对值 | 仍以报文中的原始字段为准；desktop **不转换、不归一**，语义解读仍是服务端的事 |

⚠️ **desktop 侧不改「整行透传」原则**：上面这些口径是 desktop **用来决定发不发**的，
报文里依旧是渠道原始字段，desktop 不会把算出来的 `total` 写进报文。服务端若需要
「用户设了多少房」，仍按 §3 自行计算。
