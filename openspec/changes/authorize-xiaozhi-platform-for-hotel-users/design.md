## Context

Desktop 的登录、恢复会话和主进程打开内部页面均可读取 RMS 的 `GET /api/v1/me`。该响应已有 `userType`、`permissions`、`currentHotelId`、`accessibleHotelIds`；Desktop 的共享契约对响应使用严格解析。当前内部页面仅允许 `STAFF`，RMS 的 `permissions` 则只来自启动时加载的角色权限矩阵。`HOTEL_STAFF` 有 `pricing:view`，没有 `pricing:write`。RMS 使用 `hotel_user_access` 计算酒店用户可访问的酒店，并在选择酒店及业务请求时校验。

## Goals / Non-Goals

**Goals:** 让指定酒店用户在有酒店访问权时进入小智平台并完成统一改价；沿用两个现有 `/me` 字段；确保页面展示、业务接口和撤销授权的判定一致。

**Non-Goals:** 新建 OSS 名单、第二套酒店授权范围、桌面端授权管理界面、修改其他 OTA 渠道权限。

## Decisions

1. **权限码使用 `xiaozhi:access`。** 它表示酒店用户可进入小智平台并执行该页面对应的业务流程。服务商继续沿用现有 `STAFF` 入口规则。与直接使用 `pricing:view` 相比，新码不会使所有酒店用户自然命中；与直接给个人授予通用 `pricing:write` 相比，可避免扩大其他改价接口的权限。RMS 项目负责决定内部存储和管理方式，但 `/me.permissions` 与业务接口必须使用同一份有效权限判定。
2. **复用 `accessibleHotelIds`。** 非空仅用于判断入口有可用酒店；页面酒店选择器继续使用 RMS 现有酒店列表。每个业务请求仍由 RMS 依据当前用户与酒店的实时关系校验。授权的个人权限不包含另一份酒店 ID 列表。
3. **`/me` 形状保持不变。** RMS 将角色权限与个人授权合成为 `permissions`，字段仍为字符串数组；`role` 仍表示角色。Desktop 只改变能力派生与主进程打开判据，不新增共享响应字段。当前主进程在打开时重新请求会话，能用服务端最新返回值拦截；已打开页面在会话刷新或授权变化被发现时关闭。
4. **服务端业务授权先交付。** RMS 页面自身与统一改价相关接口要处理酒店用户个人授权，同时保持原有服务商权限；不能仅让 `/me` 返回新码而沿用只按角色检查 `pricing:write` 的旧路径。具体外部需求见 [server-requirements.md](server-requirements.md)。

## Risks / Trade-offs

- **个人授权与角色缓存口径不一致** → RMS 应以用户级实时授权计算有效权限；撤销后服务端立即拒绝后续业务请求。Desktop 只能在重新取得会话时更新可见性，服务端承担最终边界。
- **新增权限码后旧客户端行为** → `/me` 的 `permissions` 仍是字符串数组，旧客户端不会因多一个元素解析失败，且旧客户端继续只向 `STAFF` 展示入口。
- **只显示页面但无法提交改价** → RMS 联调需覆盖酒店用户的页面读、计算、提交、房态房量和操作记录；逐项核对现有 `pricing:write` 拦截点。

## Migration Plan

1. 在 RMS 项目实施并验证个人授权、`/me` 有效权限和页面/接口校验；初始不授予酒店用户，保持默认关闭。
2. Desktop 对接 `xiaozhi:access` 与现有酒店列表，完成本仓库验证后发布新版客户端。
3. RMS 管理员为试点酒店用户授予个人权限，并按现有酒店授权机制配置可访问酒店；撤销时先由 RMS 拒绝后续请求，客户端随后收敛入口。
4. 回退时撤销个人授权即可关闭酒店用户访问；服务商入口保持现状。
