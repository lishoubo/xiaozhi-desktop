# 高级改价 —— 增删日期段

> 场景：批量改价 →「日期分开改价」，先选**两个**日期段并各自改价，再**删掉一个**。
> 要回答的问题：删掉日期段时美团发不发请求、发的是什么。

## 结论

**用户增删日期段时，页面会发一条 `unified/calcPriceV2`，带的是改动之后的完整日期列表。**

美团有两个试算端点，语义不同 —— 这是本次踩点最重要的发现：

| 端点 | 语义 | 响应带什么 |
|---|---|---|
| `separate/calcPriceV2` | 改了某一格的价 | **只带当次触碰的那一段** |
| `unified/calcPriceV2` | **日期范围的全量快照** | **改动后的全部日期段** |

⚠️ 别只看 `operateType` 就下结论：`unified` 的 `salePrice.operateType` 全是 `3`（不改动），
看起来像「纯查询」，但它承载的是**日期范围**这个语义。曾据此判定它与改价无关而不予监听，
是错的。

## 请求序列

```
#0 unified   两段：09-02~03, 09-08~09     ← 用户选了两个日期段（operateType 全 3，取当前价）
#1 separate  改 09-02~03 [3,4] → 55157
#2 unified   ★ 只剩 09-02~03              ← 用户删掉了 09-08~09
#3 separate  又改 09-02~03 [3,4] → 55157
```

`#2` 是关键：删除动作会触发重发，且带的是**删除后**的列表。

## 对实现的影响

累积是**只进不出**的（格子按 房型 × 日期区间 × 周次档 入键）。用户删掉一个日期段时，
没有任何东西会去删对应的格子 —— `separate` 只说「这一段的价是多少」，从不说「哪一段没了」。

**所以：见到 `unified` 就把累积整个清空。** 旧范围下攒的格子全部作废，用户改完范围必然
要重新改价（页面不允许不改价直接提交），那些 `separate` 会重新到达、累积自然重建。

实现见 `apps/desktop/src/main/channels/meituan/amount-change-adapter.ts` 的
`RANGE_ENDPOINT_ID`，决策记录见 `openspec/changes/extend-meituan-price-status-coverage/design.md`
决策 3b。

⚠️ 曾用「按提交体过滤过期日期段」解决同一问题，已废弃 —— 那要求 desktop 解读提交体语义，
而提交体有两种形状，只认一种就会返回空集，**整条上报清零**。用渠道自己发的快照做判据，
失效方式温和得多。

## 未踩到

- 用户**删掉某个房型**（不是日期段）时会不会也发 `unified` —— 房型同样是累积键的一部分，
  问题同构。若不发，那个房型的格子会残留。
