## Desktop 真机验证结论（2026-08-06）

### 结论

美团登录成功后，可以在 `https://me.meituan.com` 同源页面的
`localStorage.globalStorage` 中发现当前登录账号的 `bizAccountId`，再用同一
Electron partition 的 Cookie 调用账号详情接口，取得 credential 级账号信息。

```text
Electron partition
  -> me.meituan.com localStorage.globalStorage
  -> 匹配 req:announcementEB,key:{...}
  -> 提取 bizAccountId / partnerId
  -> GET /api/gw/v1/base/account/getDetail
  -> 回验 data.bizAcctId，并取得账号身份快照
```

这条链路已在清空 desktop userData、重新导入 Cookie 后真机验证通过：

- `globalStorage` 不是登录成功瞬间就存在；本次第 4 次轮询读取成功，轮询间隔
  500ms。实现时应允许短时等待，不能只读取一次。
- 本次只匹配到 1 个 `req:announcementEB` key，并解析出 1 个候选账号：
  `bizAccountId=274615733`、`partnerId=4595635`。
- `getDetail` 返回 HTTP 200、业务 `code=10000`；请求中的 `bizAccountId` 与响应
  `data.bizAcctId` 一致。
- 同源 XHR 使用已有 Cookie 及固定 Header 即可成功；不需要复刻抓包中的动态
  `mtgsig`、`yodaReady`、`csecplatform`、`csecversion` 查询参数。
- 本次账号详情包含 `partnerId`、`login`、`accountType`、`status`、脱敏手机号、
  区号、角色、组织和资金池状态；诊断日志未输出 Cookie、`phoneSecurityData`
  或原始 `globalStorage`。

### 数据职责

- `bizAccountId` 是美团登录账号标识，属于 OTA credential，不属于具体酒店。
- `getDetail.data` 是账号身份信息的权威来源；`globalStorage` 只作为发现
  `bizAccountId` 的桥梁，不作为长期事实来源。
- `poiInfos` 继续负责返回当前登录态能访问的 Partner/酒店 POI 范围。
- 登录账号的 `partnerId` 与酒店 POI 的 `partnerId` 必须保留不同语义，不能仅凭
  字段同名认定它们永远相等。本次样本二者相等，但其他账号样本曾出现不同值。
- 后续写入 `credentialExtra` 时应采用字段白名单；不得保存原始账号响应、Cookie、
  `phoneSecurityData`、traceId 或完整 Local Storage。

### 仍需讨论

- `globalStorage` 同时存在多个 `req:announcementEB` key 时，如何确定当前账号。
- 轮询超时、缓存格式变化和 `getDetail` 失败时的降级策略。
- credential 账号身份、可访问 Partner、OTA 酒店 POI 三层关系如何正式建模。
- 哪些账号字段需要本地持久化、同步 RMS 或只在 UI 中脱敏展示。
