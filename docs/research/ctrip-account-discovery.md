# 携程账号信息获取踩点结论

> 日期：2026-08-06
> 状态：已完成静态踩点，尚未进行应用内网络捕获验证
> 原始踩点：`docs/踩点/携程/获取账号信息.md`

## 结论

携程可以沿用美团方案的总体架构：复用用户已经登录的 Chromium Session，在浏览器页面上下文中获取账号事实，再将账号凭证和酒店账号分别写入 `OtaCredential`、`OtaAccount`。

但携程不适合直接照搬美团的“应用自行拼装 XHR”方式。携程请求包含由网页运行时生成的动态请求头和请求体上下文，优先方案应是让携程网页自己发起账号信息请求，由桌面应用捕获并解析响应。

```text
已登录的携程 WebContents
        │
        ├─ 打开账号设置页面
        │
        ├─ 携程前端生成动态参数并发起请求
        │
        └─ 桌面应用监听目标响应
                  │
                  ├─ 白名单提取账号字段
                  ├─ 丢弃敏感 token 和原始响应
                  └─ 身份字段确认后再持久化
```

## 已确认接口

账号信息接口：

```text
POST https://ebooking.ctrip.com/restapi/soa2/23515/queryAccountInfoV2
```

能够触发该请求的候选页面：

```text
https://ebooking.ctrip.com/user/setting?microJump=true
```

响应中已观察到的可用字段包括：

- `hotelCompany`
- `loginName`
- `userName`
- 手机号、邮箱、头像等个人资料

响应中还包含手机号、邮箱相关 token。这些字段不属于业务所需凭证，禁止记录日志或持久化。

## 为什么不优先自行发请求

踩点请求除了 Cookie 和同源信息，还包含以下动态上下文：

- `spidertoken`
- `w-payload-source`
- `x-traceID`
- 多个 `x-ctx-*` 请求头
- 包含浏览器、页面、UBT 和 RMS 上下文的 `reqHead`

同源 `fetch` 或 `XMLHttpRequest` 只能自动携带浏览器负责的 Cookie、Origin 等信息，不能保证自动生成携程业务层的动态字段。自行复制这些参数容易失效，也可能触发风控。

因此推荐监听页面原生请求；只有在实测确认页面请求封装能够被稳定复用后，才考虑直接调用。

## 与美团方案的异同

| 维度 | 美团 | 携程 |
| --- | --- | --- |
| 登录上下文 | 复用当前 WebContents 和 Session | 相同 |
| 账号信息来源 | 页面上下文中主动发起同源请求 | 优先捕获页面原生请求 |
| 动态业务参数 | 相对简单 | 较多，依赖携程页面运行时 |
| 推荐获取方式 | 直接 XHR | 打开设置页并监听响应 |
| 持久化模型 | `OtaCredential` + `OtaAccount` | 可复用，但字段映射待验证 |

## 字段映射待确认项

`hotelCompany` 从命名和响应结构看更像公司或组织 ID，目前不能直接认定为登录账号 ID。

登录 Cookie 中存在另一个形似用户标识的字段，但仅凭字段名不足以判断其稳定性和业务语义。首次验证应同时观察不同登录账号、同一账号切换酒店时相关标识是否变化，再决定 `otaAccountId` 的来源。

在语义确认前：

- 不将 `hotelCompany` 直接写入 `otaAccountId`。
- 不以手机号、邮箱或登录名作为稳定主键。
- 不把 Cookie 或任何 token 放入 `credentialExtra`。
- 账号展示字段可以暂存为候选值，但不作为唯一性判断依据。

## 最小验证方案

第一阶段只做诊断，不落库：

1. 在用户已经登录的携程 `webContents` 上开启目标请求监听。
2. 打开账号设置页，等待携程页面主动请求 `queryAccountInfoV2`。
3. 获取目标响应体，先校验业务响应码。
4. 仅白名单提取 `hotelCompany`、`loginName`、`userName` 和脱敏后的联系方式。
5. 日志只输出是否捕获、响应码、候选标识和脱敏展示值。
6. 明确排除 Cookie、完整请求头、原始响应、手机号/邮箱 token。

建议诊断日志结构：

```text
{
  requestCaptured: true,
  responseCode: 200,
  hotelCompanyId: "候选值",
  loginName: "展示值",
  userName: "展示值",
  mobile: "138****1234"
}
```

第二阶段在至少两个账号或账号/酒店切换场景中核对字段稳定性，确认账号唯一标识后，再设计 `credentialExtra` 和持久化逻辑。

## 安全说明

原始踩点文件包含真实会话信息和敏感个人数据，只能作为本地调试材料：

- 禁止把其中的 Cookie、token、完整手机号或邮箱复制到实现、测试夹具、日志和正式设计文档。
- 建议对原始踩点文档做脱敏处理，并使已暴露的会话凭证失效。
- 网络捕获完成后应立即将响应转换为白名单结构，不在内存中长期保留原始响应。
