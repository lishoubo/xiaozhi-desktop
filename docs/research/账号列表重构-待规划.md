# 待规划：账号列表统一重构

> 2026-08-15 记。用户明确「打算重构整个账号列表，不着急」，本文只攒需求与已知约束，
> **不是方案**。启动时走 `/opsx:propose`。

## 起因

排查携程账号显示名时发现：同一份凭证在三个地方展示，口径各不相同，且各自有各自的
临时妥协。

## 现状：三处展示，两套口径

| 位置 | 实现 | 主标题取什么 | 为什么 |
|---|---|---|---|
| 浏览器右上角指示器 | `browser/login-credential-options.ts` | **酒店名**（携程） | 「我现在在哪」，不用于选择；宽度写死放不下两者 |
| 重新登录弹窗 | `hotel-management/credential-presentation.ts` | **账号名** | 要在几个账号间做选择，用门店名会串 |
| 新增绑定弹窗 | 同上 | **账号名** | 同上 |

两套口径是**有意的**（2026-08-15 与用户确认），不是 bug —— 但它意味着同一个凭证在
不同界面上叫不同名字，用户可能困惑。重构时要正面回答这个问题。

## 已知约束

- **顶栏宽度不能加**：`clamp(136px,15vw,196px)` 写死，加宽会挤压标签区（用户明确否决）
- **滚动文字不可行**：那是个按钮，点了要弹菜单，文字移动会让点击目标漂移
- **携程一个账号可管多家门店**：所以「账号 = 酒店」这个等式不成立，多店场景下用
  门店名认账号会串
- 各渠道 `credentialExtra` 字段不统一，见 `credential-presentation.ts` 顶部表格

## 用户表达的诉求

> 「其他地方，建议都展示。」

即除顶栏外的账号列表，账号名与酒店名（及其他佐证字段）都要能看到。
`credential-presentation.ts` 目前**已经**是「title 认人 + details 佐证」的两层结构，
酒店名在 details 里 —— 重构时确认这个形态够不够，还是要更强的展示。

## 顺带记一个待改（与账号列表无关，但同属这块 UI 的技术债）

**`createWaitingUiResult` 应该按 `kind` 过滤，而不是只按 `requestId` 认领。**

现状：每个 dialog 各建一份等待表，却都订阅同一条广播通道。收到别人的信封时会走
`onUnclaimed` 报 warn —— 但那是**正常现象**，不是异常。

2026-08-15 排查时被这条日志误导过：看到「Binding candidates arrived but nobody
claimed them」以为抖音探测白跑了一趟，实际那条信封是 `reauth-ota` 的结果，探测
根本没触发（`Hotel probe` 日志为空）。

已做的小修：两处 warn 加上 `kind` 字段，不再误导。
**正经修**：`await(kind, ...)` 的 `kind` 目前只用于定类型（实现里 `void kind`），
应让它参与过滤 —— dialog 只认自己关心的 kind，别人的信封直接忽略。这样
「没人认领」才真的意味着出了问题。要动 `renderer/waiting-ui-result.ts`（三个
dialog 共用），故未在当次 change 内进行。

## 再记一个待改：`#explicitlyActivated` 的复位时机

`browser-ota-tabs.svelte.ts` 里那道闸门用于让「开 tab」压过「工作区挂载时的默认
激活」。但它在 `releaseViewportSession()`（离开工作区）时被复位 —— 而
「酒店管理页 → `push('/')` → 开 tab」正好走这条路，闸门失效。

2026-08-15 因此出过一个只在携程复现的故障（见 `adopt()` 的注释）。当次的修法是
给 `adopt()` 补上 `browser.activate()`，两条链都真的通知主进程、且 `adopt` 后完成，
结果正确 —— **但靠的是时序，不是设计**。

要治本得重新想这道闸门：什么时候该复位、并行的两条激活链谁优先。影响面涉及所有
进出工作区的场景，故未在当次 change 内进行。
