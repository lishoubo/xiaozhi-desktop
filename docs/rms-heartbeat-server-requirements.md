# RMS 定期上报接口需求

本文仅记录桌面客户端依赖 RMS 提供的能力，供 RMS 项目单独评估和实施。本仓库不修改 RMS 代码。

## 接口契约

- 新增 `POST /api/v1/app/heartbeat`，使用现有 Bearer 认证；未认证时沿用现有鉴权错误。
- 客户端不发送请求体，沿用请求头 `X-App-Version` 和 `X-Device-Id`。接口成功时返回现有 API 风格的空数据成功响应。
- 该端点只表示定期存活与版本上报，不重新登录、不签发令牌、不更新最近登录时间。现有 `GET /api/v1/me` 保持纯查询。专用路径已经标明类型，不要求 `X-Report-Type`。

## 记录与查询需求

- 认证成功后，把上报写入现有 `login_log`：`employee_id` 为认证用户，`login_type=HEARTBEAT`、`result=SUCCESS`，`app_version` 和 `device_id` 取请求头，`created_at` 由服务端生成。版本缺失或空白时记录空值；认证失败不写入心跳记录。
- 登录历史能将 `HEARTBEAT` 标为“心跳上报”，不把它当作真实登录；原有最近登录时间保持原义。
- App 用户管理页读取每个用户最新一条成功的心跳记录，展示该条上报时间和版本。距上报时间不超过两小时显示“近期运行”，超过两小时显示“未在近期上报”，从未上报显示“暂无上报”。该状态是近期活动推断，不代表实时连接。
- 同账号多设备时，列表展示最后一次上报的设备版本；设备级视图不在本次需求内。老版本客户端不发心跳时，现有登录和 `/me` 行为不受影响。

## 验收要点

- 有效、未认证、空版本和重复上报的记录行为正确；心跳不会改变登录状态或最近登录时间。
- 管理页的最近版本、时间和两小时状态边界正确；历史记录能区分心跳与登录。
- 评估每小时写入带来的 `login_log` 增长，以及 App 用户分页查询最近心跳时的索引和查询计划。
